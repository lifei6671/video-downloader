## 实现范围与原瓶颈

- 原链接下载 `telegram_download::SdkTransport` 及备份 `original_reader` 都依赖 `iter_download().next()`，每次取回 512 KiB 后才继续下一请求。链接路径还逐片 flush。网络往返期间没有主动请求窗口。
- **原上传并非全部串行**：grammers 0.11.0 的 `upload_stream` 对大于 10 MiB 的文件已固定使用 4 个 RPC worker，小文件串行。不能将新上传与“原大文件串行”比较，也不能把 SDK 的 worker 数称为 TCP 连接数。
- 新引擎在 `src-tauri/src/telegram_transfer_engine/`，分别提供原文档 `Download` / `Reader` 和上传 `upload`。复用 Tokio、已锁定的 `futures-util` 与 `md5`。没有复制 tdl 的 AGPL 实现。

## 分片、背压及完整性

下载 `Chunk { index, offset, length }` 使用 512 KiB 对齐偏移和 512 KiB GetFile 请求；最后一片仍发协议对齐请求，只接受实际剩余长度的响应。请求不跨 1 MiB 边界。`upload.file` 本身没有 offset 字段，响应通过 SDK/MTProto 的请求 ID 与请求偏移关联，不能声称验证了不存在的响应 offset。拒绝短片、空缺片、超长片及非普通文件响应。

初版按建议请求 1 MiB，真实 100 MiB 测试触发 `grammers-mtproto-0.11.0/src/manual_tl.rs:75` 的 `len < MessageContainer::MAXIMUM_SIZE` 断言。SDK 对 incoming 单 message body 使用 1,044,448 B 上限，1 MiB 文件数据加 TL/RPC 头会越界。这是确定性的 SDK 兼容失败，未归为普通网络抖动。修复为 SDK 当前支持的 512 KiB，并增加实际 TL/RPC 编码长度低于该上限的回归测试；没有扩大加密协议解析器限制。旧 1 MiB 先导结果独立归档，不混入最终矩阵。

`FuturesUnordered` 允许乱序完成。普通下载使用 `FileDownload`：每个完成片立即返回其请求 offset，由唯一写入者 seek 后写入任务暂存文件，再补充下一片；在途及完成待消费数据始终受单文件 worker 数限制。慢首片重试不再占满顺序重排窗口，进度只累计一次实际写入的有效字节，所有请求完成且长度、文件头及身份验证通过后才提交。备份继续使用有界滑动窗口的 `Reader: AsyncRead` 顺序输出，保留恢复/释放前的完整 SHA-256 核验及不覆盖提交，不为填补慢片而缓存整个文件。普通链接没有凭空增加已知原文件摘要。

普通下载每秒更新一次进度和速度，完成时立即刷新。速度使用最近约五秒的实际有效字节和经过时间计算，并在等候分片时继续采样；真实停滞会降到零，不用插值进度伪造网络吞吐。离线测试用暂停首片的确定性 gate 验证其它片继续完成、单写入者按 offset 写回、短尾片/重复完成/缺片拒绝和失败回收；计时采样测试使用注入的时间。此次没有运行网络或性能测试，不能据此声称实际带宽、失败率或 P95 已改善。

文件引用过期在 `DocumentSource` 内串行刷新原消息，核对文档 ID、access hash、大小、MIME、媒体属性。其它待完成片使用新引用，已完成数据保留；最多刷新两次，耗尽返回终止错误，避免触发外层旧接口的整流归零重试。DC 迁移更新本文件的目标 DC；非主 DC 才可导出/导入已有授权，主 DC 认证失效及导入后仍失效均返回原认证错误。

请求显式 `cdn_supported=false`。意外 CDN 重定向返回 `TELEGRAM_CDN_UNSUPPORTED`，不解密、不写入 CDN 字节，也不 panic；本轮没有实现 CDN 解密传输。

上传以 512 KiB 顺序读取，再交给有界并发 RPC；源 `SourceReader` 继续按原顺序计算 SHA-256，上传前后继续执行现有源文件核验。小于等于 10 MiB 使用 SaveFilePart 和完整流式 MD5；大于 10 MiB 使用 SaveBigFilePart / InputFileBig。随机 file_id、0 起始分片号和实际 app config 文件上限均保留，并检查分片数量的 i32 范围。BoolFalse 明确失败。重试复用同一 file_id、分片号和内容；成功确认只累计一次。UI 进度使用服务器确认字节，磁盘读取不提前推进。

上传返回临时 InputFile 后，仍经原 `Prepared → Sending → Confirmed`、random_id、富消息发布及回执核对。消息结果未知继续对账，不重新盲发。发布 RPC 明确返回 FILE_PART_MISSING 时映射为 `TELEGRAM_UPLOAD_PART_MISSING`，回到 Prepared，保留原 random_id；下一次重建临时上传后才再次发布，不把缺片当成成功或结果未知。协议版本、富消息、封面/文案、归档、墓碑及 `resumable_upload=false` 均保持。

## 预算、重试与取消

| 参数 | 当前值/行为 |
| --- | --- |
| 下载 / 上传分片 | 512 KiB / 512 KiB |
| 生产单文件默认上限 | 8，无新增 UI 或持久化设置；测试可到 16 |
| 视频备份并发 | 2，Telegram 与 S3/R2 共用两条固定执行通道；文件分片仍共用原账号预算 |
| 文件大小动态 worker | <1 MiB 为 1；1–5 MiB 至多 2；5–20 MiB 至多 4；20–50 MiB 至多 8；其余使用配置上限；再取实际片数和配置上限的较小值 |
| 测试配置 | 1 / 2 / 4 / 8 / 16，通过仅测试构建的 task-local Settings 注入 |
| 账号文件 RPC 总预算 | 初始 16，同一已核验账号的上传、原文档及封面共享；请求超时后通过 semaphore 权重将实际并发依次减至 8/4/2/1，已排队请求也遵守新预算；该预算实例内不自动升回 |
| 单文件缓存上限 | 64 MiB 业务分片窗口预算，窗口还受分片大小与 worker 数限制；生产默认重排序窗口最多 4 MiB，另有当前消费块及 SDK/协议缓冲；不是全进程 RSS 限额 |
| 请求 / 总传输期限 | sender 文件请求 60 s 无 socket 进展、599 s 总期限；外层分片及恢复探测 600 s。文件 Io 等待允许四次分片尝试及退避，共 2,410 s；普通元数据仍为 60 s 活动期限。不是整文件总时长限制，取消保持即时检查 |
| 临时错误 | 网络、超时、服务端 5xx 最多 4 次尝试；200/400/800 ms 基础退避加随机抖动 |
| FLOOD_WAIT / FLOOD_PREMIUM_WAIT | 登记账号冷却并返回原错误交由已有队列持久退避；等待期限内不发新文件请求，不提升并发绕过限制 |

账号注册表保留尚未过期的服务端冷却，即使全部任务已释放；无活动且无冷却的条目在下次取得预算时清理。认证/权限、身份变化及内容不符不自动重试。跨 DC 的 `AUTH_KEY_UNREGISTERED` 例外沿用一次授权恢复；并发失败在账号授权锁内复查 DC 授权代次，其他分片已经导入成功时直接重试，不重复导出/导入。

取消/首个不可恢复错误会停止调度，丢弃窗口内全部 future，无分片级 detached task。上传逐片确认同时刷新 Io 活动时间，尾批分片重试时不会把持续成功的确认误判为闲置。SDK 局部补丁在有文件请求时每 100 ms 释放调用方已放弃的文件请求状态，阻止继续保留/重发；已进入 TCP 的数据和服务端执行无法撤回。保留控制及发布请求的既有结果不确定语义。账号退出、代理切换和应用关闭继续由原会话生命周期终止/等待连接回收。

备份队列使用两条固定通道：主通道执行上传、删除及旧上传清理；第二通道只执行上传。领取和状态更新仍在同一 SQLite 锁内，保留原操作及重试期限，不按资产数创建后台任务。不同资产的上传共享 `backup_write_lock` 读租约，同一资产再由既有文件锁互斥；删除、本机释放及本机删除使用写租约。前台删除排队后两条通道均暂停领取新上传，等待已经开始的上传排空，再按原协议执行删除。旧上传清理仅由主通道在无活动上传时取得独占写租约执行；另一通道领取新上传后，清理让出且不计失败，不会被两个通道重复领取。

Telegram 的 `backup_transaction` 同样使用读写租约：媒体上传可并行，索引发布、归档、删除、代理替换及账号退出独占，避免同时修改频道投影或代际。上传期间只租借既有 Client/session/generation，释放连接 `state` 控制锁，不占 `backup_read`。Io 继续观察绑定、登录、代理及连接停止信号；单视频取消仅终止自己的工作，整体停用、代理切换和关闭等待所有上传读租约排空。消息身份、原 `Prepared → Sending → Confirmed` 日志、回执对账及完整 SHA-256 校验保持，文件数据上传完成不提前视为备份完成。

两路上传的索引准备通过 `Core::telegram_map_refresh` 串行执行“读取游标 → 刷新映射 → 同步投影并 observe”，等待锁也通过 Io 响应取消。此锁只覆盖索引准备，不覆盖视频数据传输；避免慢的旧 full/difference 请求覆盖较新缓存，以及旧投影在新观察证据后提交导致 `TELEGRAM_INDEX_CHANGED`。普通快照读取复用同一刷新入口；不移除原有游标、消息身份及证据校验。

### 多视频并行的影响与验证

- 固定视频并发为 2，不与下载设置中的“同时下载数量”绑定；第三个视频继续显示“待备份”。无需新增设置、数据库迁移、消息格式或备份协议版本。
- 分片 RPC 上限仍为同账号 16，媒体 TCP 总上限仍为 8，每 DC 最多 2；多个视频分摊预算，不为每个视频复制一份连接池。默认上传窗口每文件最多 4 MiB，两路最多 8 MiB，另有源读取、附件和 SDK 缓冲，不等同于进程 RSS 上限。
- 删除不打断无关已开始的上传，因此可能等待最多两个在途视频；新的上传不会越过已排队的前台删除。同一视频的重试、文件释放和删除继续互斥。
- `parallel_upload_tests.rs` 使用真实 SQLite 队列和内存 S3 provider，覆盖两路重叠、第三路背压、单视频取消、两路退出回收、删除优先。各视频内容不同，独立回读与原文件比较字节、大小、SHA-256 及回执；Session 测试用合成授权和 loopback SOCKS 请求验证多个上传租约、独立取消和代理/绑定切换回收。消息映射测试用有界 gate 和双线程执行器覆盖 full/difference 缓存顺序、等待刷新取消，以及慢旧投影不能在新观察后提交。
- 本轮仅离线正确性检查；真实 Telegram、S3/R2 网络、跨设备在线及性能验收均 `NOT_RUN`。历史串行性能样本不能作为并行备份的提速证据。

## 满下载队列时的解析连接

解析原先也调用 `download_connection()` 创建并独占新的 sender pool，在三个下载并行时继续解析会额外启动连接。现在只读解析调用 `metadata_connection()`，优先借用同账号授权注册表中的健康下载连接；没有可复用连接时才建立自有临时连接。真正的下载仍保留独立取消边界，未引入媒体专用会话或提高连接上限。解析关闭借用句柄不关闭原下载连接；原下载结束或取消导致借用连接停止时，解析按临时连接错误处理，重新获取健康连接。

解析的连接异常、请求超时或未连接最多自动重试两次，使用带抖动的短退避，并响应用户取消、账号退出和代理变化。仅解析的只读阶段使用此重试；认证、权限、身份错误及服务端 FLOOD_WAIT 不在该分支中重试，文件写入及上传发布不被重放。离线回归验证三个下载并行仍可解析、五次解析复用三个 sender pool 而不新增、借用句柄关闭不停止下载、连接回收后重新路由、注销回收、有限重试和取消。这里证明连接对象的复用及生命周期，不代替真实 TCP 数或在线吞吐测量；本次不运行性能测试。

## TCP 与 MTProto 会话结果

当前实现真实媒体 TCP 池，入口为本地 `grammers-mtsender::SenderPoolHandle::enable_media_pool`，由 `telegram_session::Connection` 使用已验证账号的 `Budget` 显式启用。每个授权会话只保留原主 RPC pool，下载与解析租借其 Client；单任务完成/取消不 quit 主池，而是释放自身分片 future，SDK 清理已关闭 oneshot 的文件请求。代理变更、授权失效及关闭仍停止并 join 原池后替换 generation。没有按任务克隆主会话，不新增 tmp_sessions/PFS 依赖。

池按 DC 保存 `media_only` 端点，每 DC 按需创建最多 2 条媒体 TCP，全账号共用 8 个媒体连接许可，空闲 60 秒回收。仅 GetFile / SaveFilePart / SaveBigFilePart 可路由至媒体池；其它 RPC 使用唯一控制路由。每条媒体 TCP 通过现有同 DC auth key 和 SDK 新建 Encrypted 状态，具有随机独立 session_id、序号及确认状态。InitConnection 包装真实文件请求，不在媒体端执行 GetConfig、登录、发布或删除方法，不分发 updates。连接建立限时 15 秒，失败回传原文件请求，沿现有有限分片重试；收到媒体端 404 或建连失败/超时后关闭该 DC 的媒体槽，先退回普通 DC 路由；10 秒冷却后由下一条真实文件 RPC 发起单连接探测。每轮最多 3 次，失败后分别等待 30/60/300 秒，长冷却后才允许下一轮，不产生后台探测流量。探测进行中其他分片仍走普通连接；只有收到实际 RPC 响应才恢复两个媒体槽，401/403 不视为恢复，FLOOD_WAIT 等错误原样传回现有账号冷却/重试逻辑。探测等待 25 秒且响应调用方取消，监控器由原池 JoinSet 持有并随关闭回收。缺少媒体端点或可复用授权 key 时保持原单连接能力，不能将回退称为多 TCP。

tdl 同样依据文件所属 DC 取得池，并不任意选择其它机房作为同文件备用源。媒体端点与普通端点在本补丁内分开缓存，未更改 vault 的授权存储格式。

离线回环使用合成 key，捕获真实 TCP 首包并依据协议解密：两条连接 auth_key_id 相同、session_id 不同，实际发送的 InitConnection 内只有目标文件方法；覆盖断线替换、新会话 ID、2 槽上限、共享连接许可、取消、60 秒空闲、关闭回收和 404 转控制路径。独立 SDK 测试使用忽略目录中的 manifest 直接指向补丁 lib 源码，因为 Cargo 不允许从主包直接测试带 dev-dependencies 的非 workspace 依赖；不修改生产 workspace/lock，不安装工具。本轮 SDK 离线回归另覆盖 404→普通连接→加密 RPC 探测成功→恢复两槽、取消探测、25 秒期限、三次周期上限和 401/403/420 错误透传，共 11 项通过。真实 Telegram 多 TCP 授权及吞吐对照为 NOT_RUN，既有下方 338 个网络样本来自早先单连接实现，不能用于宣称此池的速度收益。

参考：[Telegram 文件协议](https://core.telegram.org/api/files)、[多 DC 与并行会话](https://core.telegram.org/api/datacenter)、tdl 的 [downloader](https://github.com/iyear/tdl/blob/master/core/downloader/downloader.go)、[uploader](https://github.com/iyear/tdl/blob/master/core/uploader/uploader.go)、[dcpool](https://github.com/iyear/tdl/blob/master/core/dcpool/dcpool.go)、[tutil](https://github.com/iyear/tdl/blob/master/core/util/tutil/tutil.go)。

## 在线验收方法与证据

入口为默认忽略的 `telegram_online_tests::transfer_perf_tests::telegram_transfer_live_performance_matrix`。必须显式提供已授权 QA 配置和新工作目录；默认离线测试不会加载真实会话或发布素材。

本轮获准复用 `.local/telegram-t4-validation/config.json`。旧数据库的 backup schema 为 5，不能由当前实现直接打开；测试只读取其 vault 绑定及 Telegram 网络配置，在新目录创建当前 schema 数据库，不迁移旧库。合成 MP4 为 640×360、1 秒原视频加合法 free box，填充为确定性伪随机字节，大小分别为 0.5 / 3 / 10 / (10 MiB + 17 B) / 100 / 500 MiB；没有以可压缩零填充制造吞吐收益。

同一账号/频道/直连路径，逐轮交替旧实现和配置 1/2/4/8/16。旧下载仍执行原 SDK 顺序迭代器；旧大文件上传仍是 SDK 固定 4 worker。上传分片计时与原来的源文件前后摘要、消息发布/回执、独立回读分开记录。每个样本经原发送 journal 发布唯一素材，回读校验长度及 SHA-256，然后只按该样本的精确 RemoteDocument 回执清理新消息。

Windows 原生 Rust 测试环境：Windows 11 Pro x64 / 10.0.26200、i9-13900KF、约 63.8 GiB 可见内存；rustc/cargo 1.98.0、Node 24.19.0。中间诊断构建曾使用 `CARGO_PROFILE_TEST_DEBUG=0`；默认栈修复后的最终离线验证、全新 T4 和 500 MiB 队列使用默认调试信息构建，并明确 `RUST_MIN_STACK=2097152`。各构建均未开启 release 优化。应用代理配置为空只表示应用直连，不能证明底层网络不存在透明代理。

`samples.redacted.ndjson` 记录每次字节、耗时、有效吞吐、候选 RPC 尝试/失败/重试数、每文件并发峰值与 RPC 累计耗时。旧 SDK 没有这些内部计数，填 null，不以理论 worker 上限冒充测量。外部 PowerShell 对测试 PID 采样实际 Established TCP 数、WorkingSet、PrivateBytes；报告为整个样本（含发布/清理）的采样峰值，进程内存不是单文件缓存大小，TCP 采样也不提供独立 MTProto 会话的实测数。500 MiB 监视器显式绑定 PID、进程开始时间及可执行文件路径，防止 PID 复用；旧轮次只有样本键关联，资源峰值保守包含该键下的先导/中断尝试，不能用来推导某个有效传输阶段的精确内存。

新增逐片诊断按结束顺序保留最近 64 条，记录 index、offset、有效长度、协议请求长度、完成/失败/取消、整体耗时、RPC 累计耗时、尝试次数及最近固定错误码；取消也由 RAII 记录已发生的耗时并释放预算。这个窗口不能还原整文件的全部历史。逐片 retries 是额外文件请求次数，含迁移/引用刷新；总 Stats.retries 只计内部网络/5xx 退避，不应将两者当成同一统计。RPC failed_attempts 只计 InvocationError/超时；BoolFalse 或长度校验失败属于分片业务失败，仍明确终止，不能因 RPC 错误数为 0 就称该分片成功。

有效字节表示原文件的有效内容，不是包含重发、MTProto 加密及协议头的实际 TCP 线路字节。上传计时覆盖 SaveFilePart/SaveBigFilePart、顺序读取及当次 SHA/MD5；源文件前后完整扫描和消息发布/回执仍正常执行，但不计入该分片上传速度。下载计时覆盖定位消息后的读取入口至独立 SHA-256 读完，不以原文件大小除整项备份事务耗时冒充纯链路速度。

长跑矩阵启动于新增逐片窗口之前，保留原有请求总数/累计时间等字段，没有旧样本的 recent_chunks。前 242 个有效样本使用默认调试信息与旧 `test_probe` 入口；第 243–300 个有效样本切换为无调试信息构建，仍为 `test_probe`；后续 38 个有效 500 MiB 样本使用最终默认调试构建与生产 `upload_media` 入口。四档小文件完成后，在第 242 个有效样本处受控停止本轮测试进程，使用同一 journal 切换到新增诊断的二进制；不删除已完成有效样本、不重置 Sending、不把中断当网络失败。后续大文件样本记录最近 64 片，重启记录另存 `controlled-restarts.redacted.ndjson`。RPC 参数、分片/并发和字节流算法没有因此改变，不反推旧超时样本的具体错误类别。既有矩阵入口 `test_probe` 只证明分片策略，仍持原控制锁；新入口改用生产 `upload_media` 租借路径，后续样本与真实 T4 才用于核验新生命周期，不能用旧样本证明控制锁已释放。
