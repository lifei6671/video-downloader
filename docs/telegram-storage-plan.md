# Telegram 存储技术方案

更新日期：2026-10-31。选型：**grammers，直接集成到 Rust Core**。

状态：T1 授权、T2 原字节传输、T3 空间/队列/事件重放和 T4 删除/重新上传已实现。当前按首次实现仅保留一种存储格式和直接创建的 SQLite 表结构；无试验期兼容或迁移。Windows 本轮验收使用直接启动二进制；过往安装包及其它版本的记录不替代本轮验证。数据库快照采用本机 age 加密，在远端备份中按空间启用。实际检查与在线验证见 [实施记录](telegram-storage-implementation.md)。本轮不提交、不推送。

## 1. 范围与当前基线

核对基线为 `codex/s3-video-backup` 的 `c4a1a9b`。复用 [统一备份架构](r2-multi-device-sync-plan.md) 与 [当前使用契约](multi-device-sync-operations.md)，Telegram 是与 S3/R2 平级的独立备份提供商。视频、封面、文案和恢复索引均存入 Telegram，不依赖 R2 保存元数据。

首版沿用个人单写备份：同一用户在不同设备独立登录同一个 Telegram 账号，连接同一个私有频道，发现资料并按需恢复视频；写入设备切换前应暂停原设备并完成待确认操作。不承诺多设备同时上传、跨重启上传续传或边下边播，也不引入设备选主、全局锁或独立协调服务。事件协议保留已有冲突处理语义，并测试意外重叠写入不能静默丢失资料；正式并发协作属于后续独立验收范围。

保持现有独立空间、下载目录、资产身份、任务生命周期及本机副本规则。切换空间不自动补传历史视频，不复制 R2/S3 库，不清理旧空间。分类、标签、AI 总结及历史文档属于此前素材库工作的范围，当前分支不能视为已具备其备份映射；后续合并时另行核对，不能以本方案承诺整个素材库已可恢复。

## 2. SDK 选择与依赖策略

采用 [grammers](https://codeberg.org/Lonami/grammers)：Rust 实现的 MTProto 客户端库，不是官方 C++ TDLib 的绑定。Rust 进程直接连接 Telegram，取消此前讨论中的 Go helper 和额外 JSON Lines 传输层；不新增 TDLib 动态库、Python Telegram 客户端或本地 HTTP 代理服务。现有 PythonBridge 继续负责原有下载和媒体处理，平台下载也使用 grammers，默认复用备份账号；两处均可点击“切换其他账号”只切换当前用途，并独立持有任务连接，见 [Telegram 下载](telegram-download.md)。

选型依据：与现有 Rust/Tokio 栈一致，可直接调用用户授权、频道历史和文件传输接口，减少独立运行时及跨进程生命周期维护。项目仓库已从 GitHub 迁移至 Codeberg，不能把旧 [GitHub 仓库](https://github.com/Lonami/grammers) 的归档状态解释为项目停更。源码采用 MIT/Apache-2.0 双许可；实施时核对锁定版本及传递依赖许可并保留声明。

当前 `grammers-client` / `grammers-session` 已由锁文件固定为 0.11.0，Windows 项目编译和桌面静态检查已通过，其余平台尚未验证。后续升级继续锁定通过验证的发布版本；若必要修复仅存在于上游仓库，则锁定具体提交，记录原因，不跟随浮动分支。所有直接使用的 `grammers-*` crate 保持兼容版本，检查 Rust 工具链、Tokio、会话存储及 SQLite 链接兼容性；优先使用 SDK 重导出的 TL 类型，不复制协议代码。来源：[发布与依赖文档](https://docs.rs/crate/grammers-client/0.11.0)。

当前 [Client API](https://docs.rs/grammers-client/0.11.0/grammers_client/client/struct.Client.html) 提供验证码登录、2FA、会话列表、历史遍历、按 ID 读消息、上传、下载和底层 RPC。2026-10-31 用户要求改为与 tdl 类似的扫码体验；使用 [官方 QR 授权流程](https://core.telegram.org/api/qr-login) 的底层 RPC，覆盖过期刷新、扫码更新及跨数据中心导入，不假定 SDK 有高级扫码方法。当前不提供手机号验证码入口；接口存在不代表真实登录、大文件或重启恢复已经验收。

## 3. 架构与复用

调用方向：React / Tauri → Rust Core → 现有 SyncEngine / BackupProvider → TelegramProvider → grammers → 私有频道。

| 模块 | 职责与拟调整 |
| --- | --- |
| `backup/provider.rs` | 复用空间、媒体引用、能力、回执契约；补齐 Telegram 引用验证 |
| `backup/telegram_provider.rs` | 消息与媒体映射、事件重放、上传恢复、精确删除 |
| `telegram_accounts.rs` | 本机下载/备份账号选择、默认复用与独立切换 |
| `backup/telegram_session.rs` | grammers 连接、独立授权、会话持久化与关闭；不另建任务队列 |
| `backup/spaces.rs`、`settings.rs`、`library.rs` | 提供商配置、账号与频道身份、库初始化、凭据隔离 |
| `backup/sync_engine.rs`、`scheduler.rs`、`lifecycle.rs` | 复用任务、退避、取消；补齐待确认发布状态 |
| `backup/sync_read.rs`、`sync_delete.rs`、`conflicts.rs` | 复用懒恢复、本机保留、墓碑及冲突规则 |
| SQLite 仓储与首次建表 | 提供商专属读取位置、已处理事件、未确认发送及来源证据 |
| 设置页、Tauri 命令、事件 | 登录、选频道、连接和传输反馈；沿用现有控件及设计规范 |

源码现已接入 `TelegramProvider`、独立账号/频道配置、原始事件发布及重放确认；`SyncEngine` 对 `EventReplay` 提供商直接发布原始变更，合并只发生在重放阶段。媒体和事件共用持久发送证据，`Accepted` 不推进本机确认。SQLite 备份 schema v1 保留 S3 目标唯一约束，将 Telegram 目标与已观察前缀完整性证据分表保存。T4 已接入精确媒体清理、显式重新上传和完整回读后释放；权限与实际验证边界见实施记录。

Rust 管理 grammers 连接及其后台任务，在现有 Tokio 生命周期内取消并等待结束。网络等待不持有 SQLite/Core 锁。只有操作 ID、账号、空间及频道都匹配的回调才更新业务状态。停用空间阻止新请求并取消在途操作；不因切换页面销毁有效任务。

## 4. 应用身份、登录与会话

`api_id` / `api_hash` 标识客户端应用，用户账号授权标识资料所有者，两者分离。映取开发者通过 [API development tools](https://my.telegram.org) 申请自己的应用身份，正式分发版本由受保护的构建配置注入；不使用网上共享或官方示例凭据，不提交真实值到仓库或日志。普通用户只登录自己的 Telegram 账号，不要求每人申请一套 API ID。[官方申请说明](https://core.telegram.org/api/obtaining_api_id)

桌面二进制中的应用凭据无法保证不可提取，构建注入用于防止仓库及日志泄露，不作为用户数据的访问控制。缺少应用配置的开发构建明确显示不可用，不借用其他客户端身份。

每台设备建立专用于映取存储的会话，不导入、复制或覆盖 tdl / Telegram Desktop 的会话。以 Telegram 返回的稳定账号 ID 核验空间绑定；更换账号不能继续执行旧账号的上传或删除。多个空间可以引用同一设备上的该账号会话，但操作仍逐一核验频道和库身份。

登录过程使用扫码及必要的 2FA；密码提交后清空，不持久化、不记录日志。二维码随服务端期限自动刷新，原始 token 和登录 URI 不进入前端、数据库或日志，仅临时显示二维码矩阵；关闭或取消弹窗停止本次扫码，迟到结果不能重开账号状态。授权密钥等会话秘密通过系统凭据存储或由其保护的本地加密存储保存，选择 SDK 会话适配方式时检查实际落盘内容，不假设其默认 SQLite 会话已经加密。数据库只保留引用及必要的非秘密状态。退出账号先停止关联任务并处理授权撤销结果，再清理本机会话；撤销失败必须明确报告。

私有频道不是端到端加密空间。视频保留原始字节，MP4、MOV、MKV、WebM 等视频容器均添加 `documentAttributeVideo`，按真实容器设置 MIME，使用视频媒体展示，不自动转码或重封装。封面和文案继续以原文件附件发送，不添加视频属性。

### 视频属性与流式播放

已有有效时长和尺寸时直接复用；信息缺失时，通过现有本地 FFprobe 补齐时长、尺寸和旋转后的显示方向。FFprobe 缺失或无法识别有效视频时，返回可见错误，保留待备份任务，不伪造参数或静默改发普通文件。FFprobe 随“运行依赖 → FFmpeg”提供，此探测仅允许本地文件协议，并复用 PythonBridge 的超时、取消和进程树回收。

视频属性与 `supports_streaming` 分别判断：MP4/MOV 等 ISO BMFF 容器识别到 `ftyp`、`moov` 与非空 `mdat` 后开启流式标记，前置和尾置索引均可供 Telegram 客户端按需读取；缺失、无法识别的布局或其他容器保持关闭，但仍带视频属性。客户端能否播放还取决于原始编码。该标记不改变应用的 `range_read=false` 与完整回读校验。`yingqu-video.mov` 是 `yingqu-<kind>.<container>` 生成的远端附件名，不改变本地原始文件及字节。

SDK 开始读取上传分块时即更新字节计数；Rust 每 200ms 将进度写入原备份操作，界面下次读取后从“待上传”切换为“备份中”。视频按实际字节显示百分比，发布记录确认前最多 99%；仅上传封面或文案时使用已开始标记和不确定进度，不套用视频总大小伪造百分比。发送结果不确定或已确认的操作继续按原证据恢复，不为重取属性要求本地视频再次存在。

显式在线传输验收 `telegram_transfer_live` 的隔离配置应提供有效 `video_metadata`，或提供指向同版已打包 `video-engine` 的 `engine` 路径以自动探测。此配置在会话恢复前校验；普通离线测试不读取会话。报告中的 `video_media_requested` 表示视频发送请求，而非仅表示输入已提供元数据。

## 5. 频道、索引和文件身份

首版一个备份空间对应一个由用户创建的专用私有频道，媒体和索引共用该频道。用户登录后从有权访问的频道列表选择，不要求手填数字 ID，不自动创建或修改频道。初始化前检查读取历史、发布文件以及拟启用删除所需权限；关闭自动删除等能力不应被误报为账号不可用。

保存配置验证账号、频道及远端身份。新空间从账号和频道确定库身份，已有空间继续识别历史库描述。

| 远端内容 | 保存形式与责任 |
| --- | --- |
| 历史库描述 | 兼容读取已发布的库身份 |
| 视频、封面、文案 | 原始字节上传，同一资产的附件放在视频富消息内；各视频容器带真实视频属性展示，封面与文案为原文件附件 |
| 资产事件 | JSON 附件，记录新增、字段修改、删除和明确重新上传 |
| 单视频删除归档 | 文档附件，保存对应视频的原始事件与墓碑 |
| 加密 SQLite 快照 | 设置恢复密码后上传独立 .age 文档，换机使用备份链接和恢复密码 |

视频富消息的可见标题优先使用原视频标题（例如抖音作品标题），标题缺失或仅含空白时使用原文件名；上传开始即按本机资产信息设置，不显示本机目录。显示标题按 Unicode 字符截取至现有的 300 字符上限，完整标题继续保存在资产元数据中。后续提交更新时按合并后的资产信息刷新标题；不批量重写已有频道消息，旧版“映取备份”消息仍可恢复。

资产事件保存上传时的视频标题、作者名称及可用的作者 ID、昵称、账号名和类型；作者身份作为 `source.author_profile` 的可选字段，不携带本机头像缓存标志。来源提供作者身份时保存该对象，接收时校验其字段类型。

媒体引用沿用 `TelegramMessage`：稳定账号 ID、频道 ID、消息 ID，并携带大小、格式及 SHA-256；所有引用必须保存附件 document ID。本机 `space_id` 不作为跨设备库身份；远端引用读取后重新绑定到当前设备空间。文件名、频道名称和分享链接只用于展示，不能用于去重或越过作用域。

当前按首次实现提供唯一格式：同一资产使用一条视频富消息，后提取或修订文案及后续元数据追加到原消息，不重新上传视频。顶层仅展示各类型最新版，旧文案与不可变事件保存在默认折叠的“历史版本”中。视频和封面保持原字节。删除发布独立的单视频归档，明确重新上传创建新的视频富消息。

附件映射使用 `yingqu_bundle:1`，锚点统一为 `yingqu_asset_v1_part_<index>_<total>_<base64>`。仅解析这一格式，不读取或转换此前试验中的拆分附件、旧锚点和旧引用。映射允许同库、同资产的多个操作，事件必须有消息内序号。较大映射拆为连续完整的锚点块，缺块或历史证据变化均报错。服务端返回部分富消息时，调用 `messages.getRichMessage` 获取完整结构后解析。

读取媒体时获取原消息和最新附件信息，再核验引用。`file_reference` 可能过期，按 [官方文件引用规则](https://core.telegram.org/api/file-references) 从来源消息刷新；访问哈希及临时引用由会话侧管理，不作为永久可移植定位符。

## 6. 上传与按需恢复

上传流程：本机文件提交 → 持久备份任务 → 摘要及来源检查 → 媒体上传 → 回读确认消息和附件 → 发布资产事件 → 重放确认 → 备份完成。首次上传可以为视频、封面、文案各自记录进度；不能把上传百分比 100% 当作整个资产同步成功。

使用文档附件形式上传原始字节，不转码、不使用上传后删除本机文件的选项。`UploadMedia` 登记原文件，首个附件建立富消息，随后在同一消息 ID 中追加封面、文案及事件，原视频保留已验证的流式播放属性。事件最后加入，封存该操作；后续编辑产生新操作并追加到同一视频消息，不重写已提交事件。删除墓碑单独发布，明确重新上传创建新的资产消息。发布事件前重新检查源文件没有变化；大小确认不代表已完成远端全量摘要校验，恢复下载时必须验证完整 SHA-256。

当前官方公布普通账号单文件上限为 2 GB、Premium 为 4 GB；实现还须读取实际账号及服务端限制并处理限制变化。超过限制明确失败并保留本机文件，首版不自动切片或转码。[Telegram FAQ](https://telegram.org/faq)、[文件传输协议](https://core.telegram.org/api/files)

列表仅同步索引、文案和按需封面；播放、转录或显式下载才恢复缺失的视频。下载到受管暂存文件，检查空间和文件身份、大小及 SHA-256 后按现有不覆盖方式提交。有效本机文件直接使用。首版下载中断后重新开始，不宣称跨重启下载续传或边下边播；后续若支持偏移读取，需另验来源一致性和完整性。

当前能力声明：`EventReplay`；完整历史按固定高水位重放，`incremental_discovery=false`；`range_read=false`、`resumable_upload=false`；文件大小上限来自账号和服务；删除能力以权限及归属验证为准。MTProto 内部分块不等于应用已实现断点续传。

## 7. 事件确认、恢复与冲突

采用只追加事件，不覆盖一条全局“最新状态”消息。事件保存协议、库/资产/设备/操作身份、原始字段变化及各字段基线、媒体引用和删除意图；区分未修改与显式清空。不得把发布前预合并的完整快照当作原始编辑，避免事件重放重复合并或覆盖他人字段。复用现有合并规则，在 Telegram 适配边界验证语义。

同一频道内按逻辑修订 `(message_id << 32) | event_sequence` 重放，按 `operation_id` 幂等处理；事件序号从 1 开始，读取位置及证据键使用 i64。每轮完整发现历史，后续编辑旧消息不能被高水位过滤；投影和读取位置只在完整校验后提交。已观察事件缺失或变化时报索引完整性错误。删除和重新上传以新的物理消息排序，重新上传媒体必须晚于墓碑。没有旧物理消息修订、旧读取位置或旧文档 ID 的兼容分支。

发送前持久保存操作 ID 和 Telegram `random_id`，重试复用。`random_id` 是 Telegram 消息发送的去重参数，但不能代替应用对账；超时或连接中断后先查找已发送事件及媒体证据，无法确认时保留“待确认”，不盲目重传或宣称失败后已回滚。[发送媒体接口](https://core.telegram.org/method/messages.sendMedia)

`Accepted` 只说明远端接受事件；只有完整重放覆盖该操作，并保留实际字段或明确冲突结果，才能返回 `Converged`。这只确认当前已观察日志前缀，不意味着所有离线设备都已同步。发送成功但确认失败的操作跨重启继续核对，不能清除本机未提交内容。

不同字段合并，同字段不同值保留冲突，不按本机时间覆盖。显式解决冲突仅移除所选版本。删除后的旧编辑不自动复活资产，重新上传需明确新操作，并遵循当前删除修订和来源归属规则。

新设备从加密 SQLite 快照恢复任务列表和云端引用。登录原账号并选中频道后，粘贴数据库备份链接并输入恢复密码。应用按 ID 读取所选消息并验证密码。视频同步和按需读取仍沿用频道事件核验，已知事件被编辑、删除或引用不一致时报告索引完整性错误。

## 8. 删除、失败与资源回收

清理下载历史保留资料及备份。释放本机空间须确认远端媒体可读、无待同步修改，再移除本机副本。云端删除先确认同库墓碑事件，再清理经验证属于该资产的媒体附件；富消息只移除相应媒体，保留原事件附件及其摘要，不能因删除整条消息而破坏索引。既有拆分媒体仍按消息精确删除。仅作用于当前频道和空间，不按频道范围批量清空。其他设备的有效本机视频继续保留，缺失且实际读取时沿用按需墓碑确认规则。

网络错误、权限变化、账号退出、文件消息不存在和文件引用过期都不是删除证据。远端媒体缺失保留本机文案及资产，显示可诊断错误。首版不套用 S3 的删除索引压缩或事件自动清理策略；Telegram 历史清理能力保持关闭。

初始上传并发 1，不占下载中心的下载名额。限流遵守服务端等待时间并持久保存下次重试时间；认证或权限失败停止自动重试，等待用户处理。重试复用现有有界机制，错误沿现有固定类型传播，脱敏保留必要的 Telegram 错误标识。

取消、停用、切换空间和退出应取消实际上传/下载 future、连接 sender 和更新消费任务并等待回收，不只是停止前端进度。不能把取消已发送的消息等同撤销服务端操作；已确认属于自身操作的遗留消息按持久清理任务处理，结果未知的保持对账状态。仅清理本次操作的暂存文件，禁止清理用户下载目录。

## 9. 界面和接口边界

沿用现有备份空间 Tab、保存与切换语义。Telegram 设置展示空间名称、登录账号、目标频道、连接状态、启停和失败重试，不显示 Endpoint/Bucket。保存配置不等于启用；连接已有库不自动补传历史文件。素材库收藏与备份空间选择保持各自语义。

登录相关的开始扫码、2FA 提交、取消、退出及频道列表通过窄 Tauri 命令进入 Rust，与现有账号命令隔离。前端接收临时二维码矩阵与到期时间、脱敏账号、登录阶段、操作 ID、进度和错误，不接收授权密钥或会话文件。停止登录后迟到结果不能改变当前账号。

只复用既有备份 API 的适用部分，不强行把 Telegram 配置塞进 S3 Endpoint 字段。实现前梳理空间保存、启动校验、恢复和删除入口的 S3 专用假设；T3 的空间、队列及恢复已验证后开放 Telegram 同步入口；T4 的删除按实际权限及同库墓碑确认执行，释放以完整回读 SHA-256 一致为前提；频道事件、库描述和墓碑不清理。Telegram 存储本身不新增 MCP 账号、凭据或任意频道访问工具，MCP 范围不因远端存储接入而扩大。

## 10. 后续实施与验收门槛

以下是已授权方案的分阶段实施与验收门槛，未完成阶段不视为已实现。每阶段保持 S3/R2 回归可用，真实测试使用用户明确授权的专用账号/频道及合成媒体；默认离线测试不得访问真实会话或上传资料。

| 阶段 | 工作与通过条件 |
| --- | --- |
| T1 SDK 与授权验证 | 锁定依赖；三平台编译；扫码/2FA、二维码刷新与跨 DC、独立会话保存及重启恢复；检查落盘秘密、日志脱敏及登录取消 |
| T2 单设备传输 | 视频、封面、文案上传和回读；恢复 SHA-256 一致；限额、源变化、限流、文件引用刷新、取消及资源回收 |
| T3 空间与恢复 | 接入现有队列、待确认发布与重放；上传后崩溃/响应丢失；使用同一账号、频道、备份链接和恢复密码恢复 SQLite，再按需下载；切回 S3 不串任务 |
| T4 资料安全与打包 | 离线重连、重复/乱序分页、意外同字段编辑保留冲突；删除/重新上传、权限撤销、损坏索引；三平台打包和原生验收 |

最低集成场景：设备 A 上传视频和加密 SQLite 快照 → 设备 B 在隔离数据目录登录同账号并连接同一频道 → 粘贴备份链接并输入恢复密码，恢复任务且不预下载视频 → 按需下载并校验摘要。还需覆盖每个上传/确认阶段终止进程后重启、空间切换取消、Telegram 手工删除媒体、退出账号和已有本机副本保留。

后续基础检查沿用当前项目的 `npm run build`、`cargo test --locked --manifest-path src-tauri/Cargo.toml -- --test-threads=1`、`cargo clippy --locked --manifest-path src-tauri/Cargo.toml --features desktop --all-targets -- -D warnings`，并运行受影响的备份、Telegram 下载和浏览器用例。届时按实际分支功能调整 features，不照搬其他分支的 MCP 开关。

离线 fixture、真实 Telegram、Windows 原生、macOS Intel、macOS ARM64、安装包分别报告。账号可登录不等于大文件或恢复通过，SDK 文档不等于生产测试。解除 Telegram 门禁前必须有对应证据；实际结果以 [实施记录](telegram-storage-implementation.md) 为准。
