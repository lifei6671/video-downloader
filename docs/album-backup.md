# 图集备份与恢复

已完成的图集与视频共用现有资产、备份空间和操作队列。启用同步后，新下载图集自动登记；已有下载历史中的完整图集会补录到所选空间。只读取应用管理的文件清单，不扫描任意目录。缺少原图或配套视频的图集不会被标记为完整备份。

## 文件与协议

- S3/R2 每套图集以一个无压缩 TAR 文档备份，原始文件字节不变，不转码。归档包含版本为 1 的 `album.json` 和按清单顺序排列的原图、Live Photo 配套 MP4；原文件名、顺序、尺寸、质量来源及图片/视频对应关系保留。
- 归档格式使用 [tar-rs 0.4.46](https://github.com/composefs/tar-rs)，沿用其 MIT/Apache-2.0 许可。只启用归档读写所需能力，不引入压缩器或外部命令。
- 远端沿用协议 v2 的 `media` 引用。S3/R2 和历史 Telegram 归档的 `container` 为 `tar`；传输层既有 `video` 主媒体槽位同时承载图集文档。S3 对象名仍使用该槽位的现有布局。`fields.source` 增加 `kind: image_album` 和类型化的 `album_files`，不保存提取器临时 URL。
- Telegram 新备份以一条富文本消息展示整套图集：图片使用原生 Photo 资源，Live Photo 配套视频使用可播放的视频块，后续成员编辑同一条消息追加。无损原图与备份元数据收进默认关闭的“无损原件与备份数据”折叠区；视频块直接承载原视频文档，不再将同一文档重复作为折叠附件展示，也不逐项发送独立消息。不生成或上传 TAR 文件。保留应用下载时的原始文件名，索引记录顺序、图片/视频配对、大小、摘要及每个文档的消息和文档 ID。媒体引用使用 `telegram_album` 位置及 `album` 容器，所有成员仍受同一空间、账号和频道约束。
- 图片展示使用最长边不超过 2560px 的 JPEG 派生预览，再上传为 Telegram Photo；极长图、极宽图加留白以符合原生 Photo 的 20:1 比例限制，平台可以处理展示资源。原图和视频的恢复仍读取索引引用的原始 Document 字节，不使用预览替代原图。JPEG/PNG/WebP 复用现有图像依赖，其余已支持的原图格式通过现有受控 FFmpeg 进程生成预览。Live Photo 视频仅探测媒体属性，不转码。
- Telegram 明确以图片格式、尺寸或处理不支持的错误拒绝 Photo 时，在同一条消息展示该原始文件附件。不会为降级另发消息；认证、权限、限流、连接和上传错误仍正常传播，不以文件降级掩盖失败。
- Telegram 每个成员复用现有发送状态机，并在 `telegram_album_sends` 保存独立的稳定发送标识和确认记录。发送回复丢失或应用重启后先核对已有文档，再继续未完成成员；已知图集消息 ID 时直接读取完整消息并验证归属，已有成员不重传，确认缺失的成员追加回同一条消息。读取失败不判作缺失，首条消息结果未知时仍需查证，不盲目重发。全部成员上传并核对后才发布图集索引。取消会清理未发布且未被引用的成员，删除备份会清理该图集拥有的全部文档。
- 本机发送记录的 `first_error` 保留首次已知错误，包括脱敏后的 Telegram RPC 错误名和码；后续重试及成功不覆盖它。`last_error` 记录最近错误，成功后清空。历史上已经丢失的首次错误无法还原，`TELEGRAM_SEND_UNCONFIRMED` 只是核对结果，不作为首次发送错误补录。明确的 4xx RPC 拒绝回到待发送状态，连接中断或 5xx 等不确定结果仍先核对。升级后，仅因发送未确认而阻塞、仍有未确认成员的有效图集获得一次新的重试预算，保留全部发送证据；再次失败仍按正常次数上限停止。
- S3/R2 继续复用流式归档上传、分片、取消、重试及摘要检查，视频备份格式保持不变。
- 图集内容身份保持历史确定性摘要和逻辑大小，计算时流式散列兼容表示，不创建临时归档。每个原始成员还单独记录字节数和 SHA-256，上传与恢复均校验。S3/R2 的 TAR 头部保持固定，不受本机路径、修改时间或权限影响。
- 保持现有图集边界：最多 64 张图片，每张图片和每个配套视频最多 32 MiB。只备份下载时实际保存的文件；原图不可用时已保存的高清文件保持原质量标记，不伪称原图。

已有视频对象和历史 TAR 备份不迁移，旧 TAR 仍按原路径恢复，之前逐文件分多条消息的 Telegram 备份也继续支持读取。独立文件格式需要参与恢复的设备升级到支持 `telegram_album` 引用的版本；旧版应用不支持此引用。

## 恢复与本机操作

应用重启后，已提交的中断下载按原队列顺序自动重新开始，保留任务 ID、所选规格和已确认的重复下载意图；下载从头开始，不承诺跨启动断点续传。备份队列恢复未完成操作并先核对远端发送结果。主动取消、删除、其他业务失败和未提交的解析预览不会自动启动，停用的备份空间不会被自动启用。

列表发现及封面读取不下载图集媒体。用户点击“下载到本机”或“查看图集”后，新 Telegram 格式逐个下载到操作专属暂存目录，校验每个成员，重试保留已验证成员并复用当前成员的下载进度。S3/R2 和旧 Telegram TAR 先下载归档并验证整体摘要，再检查清单、顺序、固定文件名、长度和每个成员摘要。归档内链接、额外成员或路径不匹配均拒绝。通过验证后，将私有暂存目录提交为图集目录；已有同名文件或目录不会覆盖。

本机原图与 Live Photo 使用现有图集浏览器。恢复失败持续显示错误，不显示为完成。恢复提交中断复用现有操作记录，已提交目录通过同一清单与归档摘要复核后接回资产。

释放本机空间及删除只处理经过清单身份校验的成员，不递归删除整个用户目录；用户后来添加的额外文件保留。成员已删除、后续文件被 Windows 占用时，可释放占用后重试清理。已知归档摘要的本机读取直接验证成员，无需重新打包或额外临时磁盘空间。

数据库备份仍只保存数据库快照。它保留图集记录和数据库内图片缓存，但不替代图集媒体上传；只有数据库记录、尚未成功上传媒体的图集，不能在新设备凭快照恢复完整原图或视频。

## 验证

隔离离线测试：`CARGO_PROFILE_TEST_DEBUG=0` 后执行 `cargo test --locked --manifest-path src-tauri/Cargo.toml --lib album_ -- --test-threads=1`。关闭测试调试信息用于避开此仓库 Windows 大型测试二进制的 PDB 限制，不改变测试断言。FFmpeg 图片派生预览可显式运行 `cargo test --locked --manifest-path src-tauri/Cargo.toml --lib album_photo_ffmpeg_preview -- --ignored --test-threads=1`。

覆盖 S3 两套独立数据库的上传/发现/恢复、原图及 Live Photo 字节一致性、同名目录避让、再次释放和恢复、完整旧历史补录、损坏成员拒绝发布、确定性归档、清单路径与取消、Windows 占用导致部分删除后的重试，以及 Telegram 发送/重复确认/下载往返。Telegram 用例还检查单一消息 ID、Photo 与可播放 Video 块、默认折叠的原件和元数据、封面/文案复用图集消息，以及图片派生预览不改写原文件。消息结构断言不替代真实 Telegram 客户端验收。

浏览器入口：开发服务器下打开 `tests/fixtures/background-download.html?scenario=visual-album-backup`，执行 `playwright-cli --session album-backup run-code --filename tests/album-backup.browser.js`。覆盖 1440×900、1280×800、1024×680、云端图集恢复、静态原图、Live Photo 播放、方向键、弹窗边界及持续失败反馈。该浏览器用例模拟 IPC，归档及传输字节由 Rust 用例验证。

2026-11-22 Windows 本机恢复：经用户授权，修复程序恢复了原有 17 套卡住图集的队列。实际捕获并保留首次 `RICH_MESSAGE_DOCUMENT_INVALID (400)`，移除同一视频文档的重复展示后，原先失败的 MP4 获得远端确认。一套 13 张图片和 8 段视频的图集及另一套单图 Live Photo 均已完成全部成员与索引提交，原操作为 `completed`；本机界面的同步任务数由 17 降到 15。其余 15 套继续由后台队列处理，交付时未等待全部完成；两套已完成图集的发送记录仍保留首次 RPC 错误。本记录不将入队或成员确认等同于整套备份完成。

离线回归通过：图集 30 项、Telegram 相关 268 项、启动恢复 9 项，另有真实环境或人工入口的用例按原约定 ignored；前端生产构建、Windows 桌面 Release 编译及 Clippy 通过。首次错误跨重试/成功保留、旧未确认记录恢复、远端读取失败不重传、丢回复后按 ID 确认均有回归覆盖。

本轮真实 S3/R2、Telegram 客户端图集显示、macOS Intel/Apple Silicon 及安装包验收：`NOT_RUN`。隔离传输测试使用生成 fixture；上述 Windows 恢复为用户原有队列，结果单独记录。
