## 当前目录简化验收

P1–P6保留为历史实施记录。用户随后明确改用单人备份，不要求保留多设备同时上传或上传断点续传。本次新的验收以同一资产的视频/封面/文案共用`media/<asset_id>/`为准；文件名带内容SHA256，重新上传的删除修订只在文件名中表达。历史深层引用可读取、恢复和删除，既有数据不自动搬迁。

大文件流式分片保留，但失败/重启后从第1片上传，不读取或复用既有分片；取消及未知创建结果的残留会话必须清理，空间切换只恢复待办，不承诺恢复字节断点。下面原P2/P3/P6中并发设备会话隔离、禁止重传以及上传续传的历史验收由本节替代；未改变原文件完整性、发布失败保留已发布对象、删除、按需读取和凭据隔离要求。

## 1. 执行约束

- 只有后续明确授权实施时才执行本清单。先读取 `AGENTS.md`、新方案、本文件、`docs/development.md`、`DESIGN.md` 及当前相关源码。
- 顺序固定 P1 → P2 → P3 → P4 → P5 → P6。每阶段完成实现、必要测试及该阶段验收后进入下一阶段；后续阶段承担的集成验收不能冒充已通过。
- 复用现有 Rust、SQLite、Tauri、React、AWS S3 SDK、凭据库、下载和转录能力。S3 的 `ObjectStore`/`S3Store` 保留为 S3Provider 内部接口，新增高层 BackupProvider 与 SyncEngine 的必要边界。不要重写平台引擎，不增加服务端、设备选主、跨资产去重或任意目录同步。
- 已有角色约束应在对应契约替换后清理，不能先删权限分支再让未完成的多写协议访问真实库。开发中间态只在模拟环境验证，不作为可用版本交付。
- 删除语义固定为“从**当前**同步库删除”：发起设备明确删除自己的受管文件并写入当前空间墓碑；其它设备不自动删文件、不创建跨设备本机清理任务，也不从历史任务或远端 404 推断用户删除。远端对象回收由发起设备的持久化清理任务完成，绝不越过当前空间。
- 网络操作不持有数据库锁；沿用取消、退出、重启恢复和明确错误传播机制。所有操作绑定 `space_id + provider_type + 目标指纹`，不能因配置变更写向其他目标。一次只允许一个当前自动同步空间；切换到另一个提供商或 Bucket/Prefix 时旧空间队列暂停、数据与凭据保留，**不自动迁移历史资产、操作队列或墓碑**。
- 真实凭据不得出现在代码、样本、命令参数或日志。真实 R2 操作仅限授权配置内的测试 Bucket/前缀，不对用户生产库执行迁移或删除测试。
- 不自动提交、推送、发布或安装新工具。旧验收证据不能替代本轮测试。Telegram 只预留公共接口、数据引用类型和禁用门禁；不触发账号登录、频道创建、消息读写或下载测试。

## 2. 统一接口与首版实施边界

| 业务层 | 代码责任与约束 |
| --- | --- |
| `BackupProvider` | `open_library`、`pull_changes`、`publish_change`、`upload_media`、`download_media`、`delete_media`、`capabilities`；公共类型保持提供商中立，版本令牌/游标/续传状态不透明 |
| `SyncEngine` | 统一资产身份、基线和局部变更、三方合并、幂等提交、墓碑判定、按需恢复及用户可见状态；业务层不得调用 S3 条件头或 Telegram 消息接口 |
| `S3Provider` | 复用已有 `ObjectStore`、`S3Store`、条件写、Range、Multipart、任务恢复和权限保护。R2 与通用 S3 共享实现，通过已验证能力差异选择配置 |
| `TelegramProvider`（未来） | 仅保留类型、模块接入位置与不可选状态；后续独立验收索引频道的追加事件、顺序重放、冲突版本、墓碑、消息身份与 MTProto 媒体传输 |

**语义区别**：`PublishReceipt` 明确区分“提供商已接受变更”和“对应资产的变更已确认收敛”。S3 的 CAS 提交与 Telegram 未来的追加事件不能被统一成虚假的同步原子性。公共变更对象必须区分字段缺失与显式 `null`；媒体引用使用带提供商类型的 `S3ObjectRef` / `TelegramMessageRef`，不能跨提供商解析。

**独立空间规则**：`space_id` 为本机配置键，`library_id` 为同一远端库的跨设备身份。当前用户最多选中一个自动同步空间；旧空间的关联资产、已同步基线、未提交变更、墓碑、操作 ID、凭据和上传来源证明原样保留。连接新空间不会自动补扫旧空间所有本机资产或把旧对象搬过去，只有**新完成**的视频自动归属新空间。以后若支持手动迁移，必须另设任务与确认流程，本轮不实现。

**兼容性门禁**：S3 对象可读写、列举成功只证明基本连通；多设备写入前必须验证目标服务的原子条件创建/更新拒绝语义。Range、分片续传和安全删除等能力应按功能各自检查，不支持时明确阻断或按已确认的安全降级策略处理。Telegram 未实现，任何伪造的配置或直接 IPC 调用都不能进入生产队列。

目标：先固定提供商中立的业务协议、独立备份空间及可恢复迁移；在首版仅运行 S3Provider 的前提下，为 Telegram 留出真实可实现的边界。

- [x] 固定当前 library/record 的字段、校验、修订规则、修改来源、幂等操作 ID、冲突引用及墓碑格式。S3 的 `library.json` / records 布局留在适配器内部；业务层不依赖 ETag、Bucket 或对象键。

## P2 — S3Provider、多设备发布与上传会话隔离

目标：通过现有 AWS SDK 构建首个完整的 S3Provider，让 R2 与经过验证的通用 S3 复用同一组同步语义；任意设备可提交本地实际变化。

实施任务：

- [x] 将现有 `ObjectStore`、`S3Store`、S3 条件写/Multipart/Range 封装在 S3Provider 中，保持这些低层接口与现有离线测试可用；SyncEngine 的发布、恢复和删除路径只接受 BackupProvider 公共接口。
- [x] 本地下载/转录完成在事务内登记实际变化；导入、恢复和缓存不登记本地修改。区分视频首次成功发布与仅更新标题/封面/文案；后者不能置位本机“曾上传视频”证明。
- [x] 分离新增媒体上传与元数据发布，后者不要求本机视频存在，不触发视频恢复或重传。
- [x] 持久化操作基线及变更，完成“基线/本地/远端”三方合并，按新方案处理不同字段、相同变化和真正冲突。
- [x] S3Provider 内部通过单记录 CAS 发布，处理 `412` 回读合并、可观察的条件冲突/重试语义和未知响应结果；向上返回不透明 `VersionToken` 与 `PublishReceipt`。仅验证本机媒体记录成功提交后持久化 `ever_uploaded_by_this_device=true`，并保证与提交确认一致；失败或未决的上传不能置真。
- [x] 发布确认只清除本次包含的本地修订，不吞掉上传期间新增的文案修改。
- [x] 冲突版本以不可变内容保存，并通过记录引用跨设备发现；相同内容不制造重复冲突。
- [x] 普通取消只中止本次操作自己的 upload_id；重启只恢复该操作的会话，不接管另一设备会话。
- [x] 替换基于 role 的调度与写入校验，保留真实凭据权限、库身份、启用状态及目标隔离。R2 采用既有配置预设；通用 S3 必须验证 HTTPS Endpoint、区域、路径样式与必需 S3 API 的实际兼容性，失败拒绝启用多设备写入，不能不经验证就视为等价。
- [x] S3Provider 的流式媒体、SHA-256、不覆盖提交与分片/取消保留原有能力；不能借公共 Provider 抽象导致大文件整块缓冲、重传或禁用续传。

主要修改位置：`backup/provider.rs`、`s3_provider.rs`、`scheduler.rs`、`store.rs`、`s3_client.rs`、`repository.rs`、`record.rs`、`settings.rs`、`desktop_core.rs`、`transcription.rs`。

必要测试与验收：

- [x] 强制条件冲突、提交成功但响应丢失、提交中再次修改、断线重启，结果与队列均正确。
- [x] 元数据发布无视频请求，导入/恢复后无上传回声；缺少本机封面或文案缓存不能把远端引用清空。

## P3 — 统一 SyncEngine 后台拉取、空间切换与懒加载

目标：通过统一 BackupProvider 拉取和发布，保证当前选定空间自动同步，其他空间状态与队列安全保留；懒加载继续零视频预取。

实施任务：

- [x] 将远端刷新纳入 Rust 服务，启动/启用异步拉取；前台约 30 秒、后台空闲 2–5 分钟、失败退避，手动刷新与本地变更唤醒共用调度。业务层只调用 `pull_changes`，不直接依赖 S3 `ListObjectsV2` 或 ETag 进行同步判断。
- [x] S3Provider 内部复用分页和 ETag；通用 SyncEngine 导入时保留本机未提交变化，更新提供商不透明基线/检查点及缓存。后台见墓碑只标记 `remote_deleted`，对本机缺失资产隐藏当前库云端列表，不触发其它设备文件/资产行删除和上传回声。
- [x] 切页、隐藏窗口不停止同步；关闭应用取消实际请求并保存可恢复断点。活跃时约 30 秒拉取，后台空闲 2–5 分钟，失败退避、激活/本地变更时可唤醒。
- [x] 将元数据拉取与大媒体传输分开安排，避免长上传阻断远端更新与墓碑接收；切换选定空间时先持久暂停旧操作，在重新连接旧空间验证库身份后恢复原操作 ID 与原续传状态。

## P4 — 统一墓碑语义与当前空间清理

目标：通过提供商统一的删除事件/墓碑契约完成当前同步库的逻辑删除，保留其他设备本机视频，只在本机缺失且实际读取时处理过期同步投影。

实施任务：

- [x] 发起删除的设备先事务持久化意图、停止本机上传/恢复，安全删除自己明确选定的受管本机副本，通过当前 BackupProvider 发布墓碑；S3Provider 内部使用条件写入。离线删除显示远端待删除；墓碑长期保留，禁止原库资产复活，不影响任何其他空间。
- [x] 其他设备从后台同步获取 tombstone 时，仅持久化 `remote_deleted`、停止待上传/远端恢复及原资产文案发布；本机视频若仍有效，保留并继续允许直接本地读取。**绝不因墓碑自动删文件、移入回收站或登记本机删除任务。**
- [x] 对本机已缺失文件，确认远端墓碑后，从云端列表隐藏失效资产；后台刷新不立刻删除任何本机记录。进入按需视频读取入口（播放/外部播放/首次或重新转录/显式下载）时读取**最新** `records/<asset_id>.json` 并验证 `library_id`、`asset_id` 和 `state=deleted`，再执行记录收敛。文件或 record 404、403、断网、分页错误均不能被当作 tombstone。
- [x] 曾由本设备**成功上传媒体并发布活动记录**的资产：只清理过期的已同步本机投影、失效远端引用及可再生缓存，保留最小墓碑、已上传证明、未提交本机修改和不可再生的文案等用户数据。不得直接级联删除 `media_assets` 或当前本地下载任务。
- [x] 未成功上传或来源未知的资产：本机缺失且确认 tombstone 后只维持云端列表隐藏与不可恢复；保留本机资产记录、文案、标题、冲突版本和所有未提交变更；不做投影清理。
- [x] 含未提交本机修改的已删除资产不能通过原 `asset_id` 重新上传。持久化本机待处理/冲突标记，允许用户查询和导出；本阶段不增加自动恢复被删资产的协议。
- [x] 远端逻辑删除与对象物理清理分离。**发起删除的设备**在墓碑成功后通过当前 BackupProvider 的 `delete_media` / `reconcile_deleted_asset` 清理属于该库的媒体引用；S3Provider 内部按精确资产前缀清理视频、封面、文案、冲突对象和上传分片，持久化进度并延后核对晚到对象。其他设备只取消自己拥有的 `upload_id`；不接管远端物理清理，不在按需读取时发送远端删除请求。
- [x] 释放本机空间和清理下载历史遵守现有独立语义；无可靠云端备份或有未提交内容时，不允许误删唯一受管副本。用户显式删除当前设备本机视频仅作用于该设备。
- [x] 确认远端 tombstone 后的实际读取重复调用、后台多次刷新和应用重启必须幂等；本机视频恢复与云端删除交错时，已存在且有效的本机副本不被后台误删。

主要修改位置：`backup/lifecycle.rs`、`reconcile.rs`、`scheduler.rs`、`restore.rs`、`repository.rs`、`record.rs`，本机播放与转录的资产入口。优先复用已有状态/操作表；不建立跨设备本机文件回收、回执、回收站或自动设备清理调度。

必要测试与验收：

- [x] A 删除资产并发布 tombstone，B 本机有效视频继续本地播放，无本机删除、无视频下载、无额外远端删除；B 不会重新上传原资产。
- [x] B 本机文件缺失、`ever_uploaded_by_this_device=true`，后台见 tombstone 时仅隐藏云端列表；实际读取确认最新墓碑后才清理已同步投影，保留墓碑与未提交文案。
- [x] B 本机文件缺失、`ever_uploaded_by_this_device=false/unknown`，确认墓碑后云端列表隐藏；实际读取依然保留本机资产记录及未提交标题/文案/冲突版本，返回“云端已删除”而非尝试下载。
- [x] B 本机缺失但远端仍 active 时正常 Range 恢复；远端记录 404、403、网络异常及部分列表失败不得清理任何本机资产/文案或被误判为墓碑。
- [x] 已上传证明只在媒体及活动记录成功发布（或丢响应后远端核验成功）时写入；读者导入、按需恢复、仅更新文案、清理历史及重复刷新不会改变证明。
- [x] A 删除与 B 上传、文案修改、恢复文件提交分别交错：墓碑阻止远端复活；B 的未提交文案留在本机；其它设备既有本机副本不被删除。
- [x] A 清理自身所选空间的远端对象时能发现同库其他设备留下的旧版本；A 离线时保留清理待办，重新上线继续，不假定其他设备自动接续。其它空间的对象即使包含同名 `asset_id` 也不参与清理。
- [x] B 已知墓碑时仅中止自己的 `upload_id`，不能误取消 A 的分片会话；B 按需读到墓碑不会发 `DeleteObject`、`AbortMultipartUpload` 或另建本机文件删除任务。
- [x] 发起设备显式释放本机空间、单条历史清理与从当前同步库删除三种行为区分正确，不越界、不删除无关文件，未确认备份的唯一副本可保护。
- [x] 恢复设备对当前库的删除后，本机另一个库的资产状态、引用、基线、队列和可恢复列表保持原样；跨库版本令牌与媒体引用不被接受。

进入 P5 条件：全部按需记录收敛和关键删除交错场景通过；远端逻辑删除与对象清理的失败可以持久化重试；没有其它设备自动文件删除或本机数据遗失路径。

## P6 — R2/S3 提供商契约、空间隔离与交付验收

目标：以真实 R2 验证完整 S3Provider 业务契约，以经授权的通用 S3 测试空间验证其兼容性边界，并证明独立空间、切换与队列绑定可靠。Telegram 同步不计入首版通过范围。

## 5. TelegramProvider 后续接入准入清单（首版之外）

Telegram 是与 S3 平级的**独立备份空间提供商**，视频、封面、文案、索引事件和墓碑均存放在其私有频道/账号指定空间。不得依赖 R2 存放 Telegram 库的元数据，也不得让现有 Telegram 平台视频下载适配器代替备份提供商。

真正启用前必须另行实施并完成以下验收；本文件只固定接口目标：

- [ ] 通过 MTProto/TDLib 管理独立登录会话与私有索引/媒体频道，保证账号/频道身份校验和凭据隔离；`tdl_bridge.rs` 已有实验性 HTTP 下载服务不得直接暴露为同步写接口。
- [ ] `LibraryCreated`、`AssetChanged`、`AssetDeleted` 为持久事件；采用同一索引频道消息顺序重放，维护 `operation_id` 幂等/消息发送未知结果对账，重复/乱序/分页重连后各设备资产状态收敛。
- [ ] 删除只依赖经过验证的 `AssetDeleted` 事件；消息访问失败、文件引用过期或媒体消息不存在不等于云端墓碑。此前确定的本机副本保留及按需确认规则继续成立。
- [ ] `MediaRef` 绑定账户、频道与消息 ID，过期的 `file_reference` 从原消息刷新；证明大文件上传/恢复、断点和 SHA-256 完整性在所用账号限额内可用，超出限额明确拒绝或单独设计分块清单。
- [ ] 事件已被 Telegram 接收与客户端重放确认收敛为两种状态；同字段并发变更不会静默覆盖，冲突版本可跨设备读取；取消、退出和账号限制不会造成伪成功。
- [ ] Telegram 真实双设备在线及离线测试、隐私/限流/账号异常和操作范围校验通过后才解除“计划支持”门禁；不自动复制现有 R2/S3 媒体与墓碑。

## 删除记录自动清理与再次上传

当前产品契约增加每空间默认关闭的自动清理与保留天数（默认30，1～3650）；按实际删除时间，只将已删除记录合并至精简索引。未记录时间的历史墓碑从首次检查计时。复用现有Rust维护生命周期、作用域、CAS、失败持久化和取消，不增加服务端、设备失效或第二套任务系统。保留索引用于跨设备删除识别，允许用户显式重新上传本机仍有效的视频；旧清理任务发现活动记录时停止后续删除。

验收覆盖两个独立SQLite与设备ID、同分片并发CAS、保留边界/无时间记录、索引失败/未知删除提交、活动记录与重新上传交错、原文案保留、切空间取消/回切继续及本机策略隔离。普通与分片上传同时覆盖视频/封面/JSON的实际HTTP Content-Type。真实R2/S3及原生验收单独记录，不把离线测试等同在线通过。
