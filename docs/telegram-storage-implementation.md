# Telegram 存储实施记录

更新日期：2026-10-31。方案：[Telegram 存储技术方案](telegram-storage-plan.md)。实施起点为 `codex/s3-video-backup` / `c4a1a9b0d21da9d812df5824998447ce3aaf3846`；不提交、不推送。

## 当前实现边界

T1 授权、T2 原字节传输和 T3 空间、队列与事件重放已实现。Telegram 可显式创建/连接库、保存独立账号/频道配置、切换默认空间并沿现有 `backup_operations` 队列同步。Windows 已验证全新数据库从频道重建资料、仅在显式读取视频时下载，以及两个远端持久化位置强制终止进程后的恢复。T4 已接入同库墓碑确认后的精确媒体清理、显式重新上传、完整回读后释放本机副本和取消附件清理。已删资产的事件归档到库级记录后清理原消息；频道消息映射按 Telegram 更新位置增量刷新，全新数据库仍从频道重建。远端快照与活动资产历史压缩未实现；平台与原生验收分别记录。

- `backup/telegram_session.rs` 与 `backup/telegram_qr.rs`：grammers 0.11.0 直连，按用户最新要求改为扫码及必要的 2FA，不再提供手机号验证码入口。使用 `auth.exportLoginToken`，按到期时间或 `updateLoginToken` 刷新；跨 DC 时先持久化目标 DC，再 `auth.importLoginToken`。原始 RPC 成功后显式保存已核验的 self peer，系统凭据写入失败不得发布 Ready。扫码最多等待 5 分钟，单次请求 60 秒超时，SDK 自动重试关闭，限流返回服务端等待秒数；T2 传输的账号级等待期限写入 SQLite，现有队列据此安排重试，认证/权限等错误阻断任务等待处理。
- `backup/telegram_vault.rs`：独立系统凭据服务 `com.yingqu.desktop.telegram-storage`，以本机库的 device ID 隔离会话。每个数据中心密钥独立小条目，元数据记录主 DC 与账号绑定，不创建 SDK SQLite 会话文件，不把授权数据写入应用数据库。其它 peer 与更新缓存仅在内存；后续备份历史位置由业务仓储负责。
- 登录弹窗与 tdl 共用二维码显示组件，保留现有 Dialog 与两步验证交互。二维码编码复用 `qrcode`，不自研编码器；原始 token、URI、2FA 和应用 hash 的本应用临时副本使用 `Zeroizing`。前端只得到临时二维码矩阵/到期时间、阶段、操作 ID、账号 ID/名称、频道 ID/名称及权限标志，不得到会话密钥、access hash 或原始登录 token。二维码矩阵也属于临时登录数据，不写文件、不截图存档、不记录日志；SDK 内部副本遵循其自身生命周期，不能声称全部内存副本都由本应用清零。
- 取消先发信号，再等待当前请求 future 结束并关闭 sender pool。普通退出应用保留可恢复的会话；显式退出账号先撤销远端授权，失败保留本地状态以便重试。撤销成功后的本机清理先记录 revoked 标记，部分清理失败可跨重启重试，不重新连接已撤销的密钥。
- 切换设置页不自动退出账号或销毁已授权会话。频道列表只读取 dialog，不创建频道、不发布测试消息。选择频道本身不写消息；显式创建或连接后保存独立目标配置。历史读取与实际上传已验证，删除入口依据连接时保存的权限显示，执行时重新核验实际权限。

## 正常退出后的取消提示修正

旧版发现循环会把正常退出的 `CANCELED` 写入空间 checkpoint，切换至远端备份时被通用错误映射显示成“依赖操作已取消”。发现循环现在将取消作为控制流处理，不写入空间错误，也不覆盖之前的真实错误。空间摘要读取忽略旧版遗留的 checkpoint `CANCELED`；其它同步、连接和清理错误继续显示，不修改实际 checkpoint、媒体或凭据。

回归覆盖取消不落盘、不覆盖真实错误、旧状态读取以及真实发现错误持久化。直接启动版本为 `1.7.2-telegram.7`，目录 `.local/telegram-cancel-fix/app/`；本次没有改动富消息实验或正式上传格式。

验证：190 项备份回归通过，10 项在线测试默认忽略；Clippy、前端构建与两个 Release 构建通过。Windows 隔离 B 副本在 1280×800 验证：暂停同步并注入旧 `CANCELED`，数据库原记录仍存在时，冷启动及三轮下载任务/设置往返均展示频道摘要，没有取消误报或虚假连接进度。界面版本确认 `.7`；测试进程按准确路径关闭，原测试设置及错误恢复。此项是旧状态展示验收，不代表新一次真实登录、在线传输或正常托盘退出验收。构建脚本同步设置前端 `APP_VERSION`，随附资源与当前来源逐文件核对；正式标识副本本轮未另行运行，未安装、提交或推送。证据位于忽略的 `.local/telegram-cancel-fix/`。

## 富消息接入正式备份队列（`.8` 验收）

`1.7.2-telegram.8` 将富消息从能力实验接入正式 `GrammersTransport.send`。现有队列、逐附件持久发送证据和事件 JSON 协议保留：`UploadMedia` 不产生频道消息，首附件建立一条富消息，后续附件通过 `EditMessage` 加入同一消息，最后加入事件并封存。新一次完整备份含一个视频、原始封面、文案 JSON 和元数据事件；缺少封面或文案时按实际资料保存。标题、作者及可移植作者资料仍由原事件字段携带。不会转码视频或把封面转为有损照片。

真实服务端会重建普通 `message.text`，因此不能用它持久保存附件映射。正式实现使用富消息内版本化的 `pageBlockAnchor`，编码文档 ID 与各附件的 Envelope；读取只相信这一结构，校验唯一种类、文档身份、大小及作用域。普通摘要只作展示。新引用携带 document ID，同一消息内分别回读与恢复；新旧消息格式可在同一库重放。扫描沿用实际请求取消与活动时间检查，不把持续分页误判为空闲超时。[Telegram 锚点结构](https://core.telegram.org/constructor/pageBlockAnchor)。

取消和未知发送结果继续先按持久证据查找，不盲目重传。删除先提交墓碑；对于富消息，只移除经验证的媒体附件，保留不可重写的原事件，后续重放仍可识别删除及重新上传。旧版拆分记录不自动合并；已部分上传的旧任务继续使用原回执。所有继续读取或写入这个新格式频道的设备都须升级，新版读取旧格式不等于旧客户端支持富消息。

验证：195 项备份回归通过，11 项在线测试默认忽略；Clippy、两次前端类型/生产构建与两个 Release 构建通过。真实“知识库”QA 队列用 20,498,841 B 原视频、26,458 B 原封面、文案及含作者/标题的事件完成同消息四附件确认。另一设备首次导入仍无视频路径，封面、文案一致，按需恢复视频 SHA-256 与原件一致。删除后三份媒体消失，原事件和墓碑继续可重放；另一设备用保留的本机原件执行新操作，直接产生一条新的四附件富消息。续传、恢复、删除、全新重新上传四个阶段分别通过，用时 103.11、98.68、116.49、141.17 秒。

首轮原型把索引放在普通摘要，真实服务端重建摘要后未能回读，因此未算通过，也未盲目重发。该轮唯一 QA 消息经原字节全量 SHA-256 及唯一来源核验后，只在测试代码中补入结构索引并回读，随后沿原发送证据续传；后续新操作的重新上传未调用此测试修复流程。正式代码不含这项测试修复能力。

## 构建与本机应用身份

开发者使用自己的 Telegram App API ID/hash。根目录 `telegram-app.local.json` 已被 `.gitignore` 排除，开发构建可读取：

```json
{
  "api_id": "填入自己的 API ID",
  "api_hash": "填入自己的 API hash"
}
```

仅 debug 构建读取该本机文件。正式构建必须由受保护构建配置提供 `YINGQU_TELEGRAM_API_ID` 和 `YINGQU_TELEGRAM_API_HASH`；环境配置优先，不混合两个来源。修改后需要重新编译 Rust。桌面 release 构建在 Rust 构建入口强制校验：缺失、非正 `i32` 整数 ID 或非 32 位 ASCII 十六进制 hash 均直接终止编译，错误只列环境变量名和格式要求，不输出身份值；npm、Tauri CLI 与直接 Cargo 编译均受此检查约束。debug 构建仍可不配置身份，此时账号界面显示应用身份未配置；不回退到公共身份。此文件仅放应用身份，不放手机号、验证码、2FA 或用户会话。

`build.rs` 把私有常量写入忽略的 `OUT_DIR/telegram_app.rs` 后编入二进制，不把密钥值作为 `cargo:rustc-env` 输出或前端变量。构建目录和二进制依然可能包含应用身份，不应上传开发构建目录；应用身份不是用户数据访问控制。许可清单通过 release resources 随包分发。

新上传视频从本次备份捕获的原封面生成 JPEG 预览缩略图（最长边 320px，低于 200KiB），随视频文档的 `thumb` 提交。富消息的 `PageBlockVideo` 只引用文档，使用该文档缩略图展示预览；不额外发送照片消息。完整原封面继续作为原字节附件备份，视频和原封面摘要、发送身份、恢复及删除流程不变，不转码视频。缺少捕获封面时仅在当前备份空间查找已保存封面；没有封面时沿用原上传流程。缩略图在媒体发送 journal 进入 `Sending` 之前完成上传，失败沿现有上传重试处理。已经确认的视频消息不为补封面重新上传。

## 删除批处理与耗时记录

本机按备份空间、账号、频道和库保存消息映射。映射包含素材、库索引和删除记录的消息 ID、附件身份，以及已验证的索引正文。归档前、归档确认和清理后均检查 Telegram 的频道更新位置 `pts`。收到完整增量且频道位置前进时，将发送回执（`updateMessageID`）里的正式消息 ID 与新增、编辑和删除的消息 ID 合并去重，按 ID 分批回读，并在同一 SQLite 事务内更新对应条目和位置。普通删除无需翻页读取频道历史。新设备、升级后首次建立映射、变更记录不完整时完整扫描。全量扫描以远端消息清单为准。仅当备份目标、消息 ID、附件 ID、大小和完整 caption 均匹配，且本地正文的长度与 SHA-256 通过核验，才复用正文；其余索引从 Telegram 读取。同次删除的发布刷新若实际下载并校验了新归档，清理前按 ID 向 Telegram 核对同一消息与附件，再重放已回读的正文。重试、后台复查或只有本地映射时重新下载归档。遇到远端身份或归档确认不一致时，删除操作可丢弃该空间的映射，从已持久化阶段重建核对一次。权限和网络错误沿原任务传播。


归档原始事件并确认后，按物理消息 ID 合并该资产的视频、封面、文案与已归档事件。批处理前校验同库删除修订、引用和代次，未知旧引用仍完整回读校验；执行时重新读取每条消息，要求全部附件的文档 ID、大小和 caption 与计划完全相同，才一次删除整条消息并回读确认。包含未知附件或新代次时停止，不退化为盲删。最后刷新频道变更并确认删除修订不变，之后才清理本机文件和隐藏原卡片。失败沿原操作重试；已消失的消息幂等处理，已完成删除不因启动而重新排队。

`backup_operations.payload_json.timings.foreground` 和 `timings.maintenance` 分别保存前台删除与后台复查最近一次各阶段的 `elapsed_ms`、`outcome`、时间与 attempt，包括排队、写入锁等待、发布、远端清理、扫描、索引读取、归档、消息删除、回读校验、本机清理和总耗时。取消也记录阶段已耗时间；记录不包含频道、标题、路径、账号或凭据，记录失败不将删除成功改成失败。

Telegram 删除的明细使用 `publish_` 和 `archive_` 前缀，均保存在发起删除的操作下。`upload` 记录上传索引文件，`send` 记录发布对应消息，`receipt` 记录按 ID 回查或对账并核对附件。发布前定位用 `publish_locate`，发布后的索引回读和重放用 `publish_refresh`。直写归档的上传、发送及首次重放计入 `publish_` 各步骤；清理复用该归档。需要另行归并旧格式时的映射刷新用 `archive_refresh`，确认归档用 `archive_confirm`，复用发布回读时在远端清理明细中记 `archive_identity_check`，重新下载时记 `archive_body_download`，清理全部被取代的旧库索引用 `archive_delete_old`。各子项包含在父阶段总耗时内。只记录实际执行的步骤，按 attempt 和时间区分最近一次执行与之前的重试。

发布和归档后的两次刷新各自把分解写入父计时的 `details` 字段。`steps.channel_changes` 记录等待 Telegram 返回频道变更，`steps.by_id` 记录按 ID 分批回读消息（含补读富消息和解析），`steps.index_download` 仅在索引正文缓存未命中时累计下载、校验及文件引用重试。每项含累计毫秒数和调用次数，未执行的项省略。`full_scan` 表示本次是否选择全量扫描，原因区分缺少映射和增量不可用；`steps.history` 单独计量读取起点和遍历历史，不含索引正文下载。`reused_index_bodies` 记录全量扫描复用的本地正文数。增量不可用时，`difference_reason` 区分返回不完整、位置过期或异常、删除更新频道不符，以及无法处理的更新类型（只记录 Telegram 构造器名或错误名）。发布和远端清理父阶段各自的 `details.steps` 另记会话就绪、等待会话锁、检查重连、账号核对、频道定位、频道可读性探测及上传限制配置请求的耗时和次数。`details.session_lock_holders_ms` 按请求类型记录与等待区间重叠的持锁毫秒数。发布与远端清理优先用当前账号会话的频道引用按 ID 获取最新频道资料、核对私有状态和权限；缺少可用引用时才遍历会话列表。`channel_by_id` 和 `channel_dialogs` 是 `channel_lookup` 的子计时。父耗时还包含本地数据库及其余处理。同一次删除的清理阶段可以复用发布阶段从 Telegram 取得的上传限制，命中记为 `app_config_reuse`。会话、账号或 Premium 状态变化，以及单独恢复清理时，重新请求配置。独立旧库索引按 ID 读取一次，使用同一条消息识别类型和核对附件；删除后再次按 ID 确认消失。资产和事件消息的 `remove_messages.details.steps` 分别记录删除前回读核对（`read_owned_message`）、删除请求（`delete_message`）和确认消失（`confirm_message_gone`）的累计耗时和批次数。一次视频删除先按物理消息 ID 分组，每批至多 100 个 ID；确认所有仍存在的消息都与预期附件完全匹配后，再批量删除并按 ID 确认全部消失。回读时已消失的消息直接跳过，残留或未确认时保留前台任务重试。

Telegram 视频尺寸/时长探测和无远端封面时的抽帧均由 Rust 直接执行 FFprobe/FFmpeg，沿用本机工具安装与取消回收规则；这些传输辅助操作不启动 Python。原视频和封面字节、上传媒体属性、预览缩略图与备份恢复协议保持不变。

## T4 资料生命周期

`telegram_lifecycle.rs` 在现有提供商、队列和原始事件重放上实现媒体归属核验，不新增依赖或任务系统。

- 释放本机视频前，读取原消息及附件，完整回读所有字节并校验大小、SHA-256。文件引用过期只重新开始一次；失败、取消、待同步变更或删除意图均保留本机文件。流以 64 KiB 缓冲读取，不另存整段校验副本。
- 删除先持久保存意图并保留原任务，发布同库墓碑并完整重放确认，清理全部受管远端媒体和资产消息后，才删除发起设备明确选定的本机副本；其它设备有效本机视频保留。`tombstone` / `objects` 为远端阶段，`local_cleanup` 为本机文件阶段，`finalizing` 将任务删除、历史隐藏和 `local_cleanup_done` 原子提交，提交后才发任务移除事件。失败保留当前卡片、阶段和错误；旧 `local` 阶段恢复时也先处理远端，`cleanup_verify` 的三轮清理及既有延后间隔继续存在，但不再显示为尚未删除的卡片。删除入队只通知任务队列。同一空间有可执行或执行中的前台删除时，定时、窗口唤醒和手动刷新都暂缓新的频道变更拉取。这批前台删除结束后，后台补拉一次，等待中的手动刷新共享该次结果。
- 本地 SQLite 的 `backup_pull_runs` 保留最近 1024 次实际调用 `pull_changes` 的记录。每行含空间、触发来源、开始和结束的 Unix 毫秒时间、启动时同一空间是否有待执行或执行中的前台删除，以及调用结果。定时同步为 `scheduled`，窗口唤醒为 `window_wake`，手动刷新为 `manual_refresh`，批后补拉为 `post_delete`；启动和其他后台通知分别为 `startup` 和 `backup_wake`。仅排队或被合并的请求不单独计数。结束时间为空表示尚未记录返回，进程被强制退出也可能留下这种记录。
- 同一备份空间的完整拉取和本地导入成功提交后，30 秒内的窗口唤醒跳过远端拉取。跳过不会推迟已排定的同步；从后台切回时，至迟在该次成功满 30 秒时恢复前台定时拉取。手动刷新和批后补拉沿用原有调度。可通过 `backup_window_sync.last_skipped_ms` 核对该空间最近一次跳过窗口唤醒的时间。
- 已开始的拉取继续完成，后台删除复查、尚未到期的重试及其他空间的删除不阻塞当前空间。队列每次成功执行任务后立即检查下一项已到期工作，空队列和错误沿用等待机制。队列优先执行尚未完成本机清理的删除，再处理上传，最后处理后台复查；新删除不会先等待历史取消上传的收尾。重启保留未完成操作的恢复和失败重试，不再重新排队已完成删除。每次远端清理仍重新校验同库墓碑修订、媒体归属与在用引用，不做频道清空。映射中只保存持久身份和元数据，Telegram 临时文件引用留在内存。投影继续校验库身份和已观察的事件摘要，删除目标消息前按 ID 核对实际附件；归档取代原消息前按 ID 回读核对库索引。
- 同一空间连续删除时，每条仍发布单独归档。若第一条归档已通过远端核对和重放且队列已有下一条，先持久记录删除修订和后继任务，再领取第二条。第二份归档须能重放两条删除的原修订；核对每个原视频的附件归属和存活引用后，按物理消息 ID 分批删除和确认。成功记录共享清理的操作 ID 和消息数，本地收尾仍按任务执行。后继失败时前一条可独立恢复。任务的 `initial_queue_ms` 和 `foreground_elapsed_ms` 分别记录首次等待和从首次执行到前台完成的墙钟耗时，包含交接后的等待。
- 新删除每项独立发布一份库归档，直接在可选字段 `direct_delete` 中保存完整删除事件正文。首次用归档消息 ID 和序号 1 确定删除修订；以后并入其他归档时将该修订和原字节固定到 `archived_events`。数据库中的旧检查点和独立墓碑仍可重放；升级时已经预留独立事件发送身份的任务沿原发送路径恢复。远端已接受直接归档而本机缺失回执时，先重放并核对操作 ID、正文摘要和已映射的归档附件，复用原发送身份。参与同步的设备需先升级支持新字段，旧版读取器会拒绝含新字段的库。
- 清理前将该资产原始事件按原复合修订和原字节写入库级 `yingqu-library.json` 的可选 `archived_events`，先合并全部既有库级档案与本次事件，按原修订排序并精确去重，优先复用字节完全相同的现存档案，否则使用内容寻址的持久发送身份；在同次发布已从远端回读时核对当前消息、附件 ID、大小、完整 caption 和正文，否则重新下载并逐字节确认完整归档，单独重放其中的事件并确认目标仍是预期删除修订后，清理已被该档案覆盖的旧库级索引，再删除原视频/封面/文案/事件消息。分步清理和重试沿用相同合并内容，不因原消息减少而另建档案；单写入流程最终仅保留当前一份库级索引。最后剩余消息必须只含已归档的精确事件附件，消息 ID、文档 ID、字节数及 caption 任一不匹配则停止。重放合并实时与库级事件，相同修订只接受完全相同的字节；旧 cursor 的摘要覆盖校验保持。只剩档案时也以已验证归档修订计算重放高水位，重启或全新数据库仍可恢复删除状态。单份索引沿用16MiB上限，超限明确失败并保留原消息和本地文件。旧库描述缺省无档案；写入档案后的库须由支持此字段的新版读取，旧程序不支持回退。
- 新引用保存不可变附件 `document_id`，拒绝手工替换后的附件；旧引用和未发布遗留附件需要完整回读摘要后才能清理。远端缺失消息可以幂等确认；权限、连接或内容变化不能当作删除成功。grammers 0.11 的 `Some(MessageEmpty)` 归一为文件不存在，避免成功删除后被误判为仍有附件。
- 附件 caption 的可选 `generation` 保存最近墓碑修订。明确重新上传捕获当前墓碑基线并生成新媒体和事件；旧编辑不能跨越删除边界，旧清理跳过新代次附件。删除已经被重新上传替代时，旧任务直接完成，不再移除本机或远端文件。第二次删除使用新的操作 UUID，避免改写已追加事件。
- 发送前将操作、资产、类型及设备身份写入原队列 resume 状态。取消仅清理该操作已确认或按精确 caption 对账的附件；事件已发布或被其他事件引用的附件保留，未知结果继续待确认。已清理的取消操作保留旧发送证据，再次上传使用新操作身份。
- 老 journal 的新字段缺省为 false；老 caption 不添加空 `generation`，老媒体回执不补写 `document_id`，确保跨版本重试仍复用原随机 ID 和事件字节。没有修改已有表结构，也没有转换或丢弃旧证据。
- 设置摘要提供 `can_delete_owned_media`；界面按连接时权限显示删除操作，执行时再检查实际权限。缺权限的当前库成员不会显示实际无法执行的“删除本地视频”，仍保留完整回读后释放操作；下载记录行和纯资产行采用一致门禁。缺少删除权限不阻止读取或传输。权限、附件身份、摘要及索引错误阻断自动重试，原因沿固定错误文案显示。

离线用例覆盖完整校验失败保留本机文件、替换附件、损坏索引、删除响应丢失、三轮幂等清理、另一设备本机保留、显式重新上传、旧删除重试、第二次删除、发布后的取消保护、未确认发送、旧代次遗留与新代次附件隔离、取消清理后重新上传，以及旧 journal 字节兼容。重复/乱序事件、同字段冲突、确认丢失后恢复及空间切换继续由 T3 用例覆盖。

## T2 单设备文件传输

`backup/telegram_transfer.rs` 复用 `Scope`、`MediaSource`、`MediaRef`、`UploadReceipt` 与现有源文件摘要函数；`telegram_transport.rs` 仅适配 grammers。入口为 `TelegramSession::upload_media` 和 `restore_media`，本阶段不新增 Tauri/MCP 文件操作、不接入资料库队列，也不把媒体回执当作资产同步完成。

- 视频、封面、文案均使用原字节文档附件，不转码、不删除原件；视频预览另附由原封面生成的缩略图，原始封面附件仍完整保留。检查当前稳定账号、私有广播频道、历史读取和实际发布权限；缺少删除权限不阻止传输。账号 Premium 状态及服务端 `upload_max_fileparts_*` 决定单文件上限，无法读取限制则失败，不猜测限额。
- 上传前保存文件大小和 SHA-256，上传读取时再计算一次，所有分块确认后重新检查本机源文件；源文件变化时不发布消息。当前 SDK 接口不暴露逐块确认进度，媒体字节进度在所有分块确认后更新；仍需原消息与附件回读确认才能返回上传回执。

- `telegram_transfer_cooldowns` 保存账号级重试期限；等待期内不发起传输网络请求，重启后仍有效。不自动循环重试。历史对账分页有实际进展时刷新 60 秒闲置期限；文件传输随实际读取进展刷新，避免把大文件一律当作 60 秒超时。

## T3 空间、队列与事件重放

`telegram_provider.rs` 实现现有 `BackupProvider`，由 `spaces::provider` 按提供商选择；Telegram 与 S3 共用 `SyncEngine`、后台队列、发现循环、冲突合并及 `sync_read` 暂存提交。本轮未新增第三方依赖、独立协调服务或第二套任务系统。

- SQLite schema v5 将 S3 目标的全表唯一约束改为 Endpoint 非空时的唯一索引，保留既有 S3 行、凭据引用、任务和 T2 发送证据。`telegram_spaces` 独立保存账号/频道及未完成初始化状态。建库前持久保存本机空间与库 UUID，失败重连复用相同身份；频道缺库时普通连接明确失败，只有显式创建才能发布描述。
- 库描述和事件都是带大小与 SHA-256 的 JSON 原字节附件；事件保存原始 `AssetChange`，不保存发送前预合并快照。序列化时去除本机空间 ID，读取时重绑定当前空间，校验账号、频道、库、资源类型和字段。视频、封面、文案继续使用 T2 传输与原发送 ID，跨重启确认后不再分块上传。
- `SyncEngine::publish` 对 `EventReplay` 直接发布原始变更；`telegram_replay` 固定当前高水位，完整读取该范围、按消息 ID 排序并按操作 ID 去重后才产出投影。沿用既有字段基线和冲突保留规则。允许消息 ID 间隙，删除非索引的顶部消息不能单独触发索引损坏。
- 发送接受与本机确认分离。只有完整重放覆盖操作后才返回 `Converged`；`Accepted`、不完整发现和失败均保留待同步编辑。`telegram_observed_prefix` 独立持久保存已观察事件 ID/摘要，确认后立即退出也能识别已知事件缺失或改动；它不提前推进业务拉取 checkpoint。投影、资料导入和业务读取位置仍由原有事务提交。
- 同一 grammers 会话串行处理请求；流读取通过有界管道衔接既有恢复接口，不先下载整段视频至另一份临时文件。放弃流或停用空间会停止实际请求，后台连接沿用当前空间检查、120 秒准备期限和关闭回收；交互扫码、连接及 2FA 阶段不会被后台恢复登录覆盖。
- 小文件和视频读取中的 `FILE_REFERENCE_EXPIRED` 各重新取得原消息并从零重试一次；视频丢弃本次受管部分文件的读取位置，再走大小、SHA-256、媒体头和不覆盖提交。有效本机视频优先复用，读取列表、文案和封面不创建视频恢复任务。
- 现有有界队列继续负责重试。Telegram 限流使用服务端等待秒数，认证、权限、上传限制与索引完整性错误停止自动重试；切换默认空间冻结旧任务，不改旧目标、媒体或恢复证据。T3 验收时不发布快照，能力声明 `incremental_discovery=false`、`range_read=false`、`resumable_upload=false`、`can_delete_owned_media=false`。
