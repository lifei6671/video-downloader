# 多设备云端备份与同步架构方案

日期：2026-10-30

状态：保留原始架构设计与实施依据；当前媒体上传范围已按下述个人备份约定收敛，实际验证见验证记录。

代码基线：`codex/s3-video-backup`，`ed24459`。

实施任务：[P1–P6 实施任务与验收](r2-multi-device-sync-implementation.md)。现有实现与历史验收分别见 [S3 备份方案](s3-video-backup-plan.md)、[M1–M6 实施任务](s3-backup-implementation.md)、[验收记录](s3-backup-validation.md)。本方案定义统一备份提供商架构，首版由 R2/S3 提供商承载多设备同步；Telegram 适配采用后续独立阶段。当前仍属设计文档，不表示客户端已支持多写或新提供商，也不授权迁移真实库。

## 当前媒体上传范围

用户已明确取消保留多设备同时上传和上传断点续传的要求。S3Provider的新视频、封面、文案统一存入`<Prefix>media/<asset_id>/`，文件名为`<kind>-<SHA256>.<ext>`；重新上传只在文件名增加`r<删除修订>-`。不再使用内容哈希、设备ID、操作ID的多层目录。旧键继续按记录读取和删除，不自动迁移生产对象。

流式分片仍用于大文件，每次失败/重启重试清理未完成会话后从第1片开始，不接管旧分片；持久化状态仅用于取消/清理，`resumable_upload=false`。单人使用时保留现有后台队列、记录身份、发布确认、空间隔离、按需恢复、删除与本机未提交内容保护。下面的初始方案和P1–P6历史记录不再构成保留并发设备媒体上传与上传续传的验收要求；当前操作契约见[维护说明](multi-device-sync-operations.md)。

## 1. 目标与范围

用户在 R2、通用 S3 和后续 Telegram 中选择一个备份提供商，连接该提供商下的**一个独立备份空间**。连接到同一提供商、同一库的设备平等读写；任意设备新增视频可自动上传，其他设备自动发现资产及元数据，视频本体仍本地优先、按需恢复。删除遵循**云端逻辑删除、其他设备按需确认**：经权威墓碑确认后禁止旧资产复活，保留其他设备已经存在的本机视频。

继续使用现有 Rust、SQLite、Tauri、React、系统凭据库及下载和转录能力。**首版通过现有 S3 SDK 接入 Cloudflare R2，并对满足必需条件写入能力的通用 S3 服务开放连接**；Telegram 作为独立提供商预留接口，不在本轮实现其上传、元数据或同步能力。客户端直连选定提供商，不增加独立协调服务、设备选主或全库写锁。设备 ID 只负责修改来源、操作归属和诊断。

本轮仍只同步应用管理的已完成视频、封面和文案。不扩展任意目录扫描、图集同步、跨资产物理去重、边下载边播放或通用协同编辑。独立下载产生的不同 `asset_id` 保持不同资产，不仅凭来源链接合并不同清晰度的视频。**每个备份空间独立保存资产索引、远端版本、墓碑、上传证明和操作队列；切换提供商不自动迁移媒体或同步状态。**

## 2. 用户操作与文件生命周期

| 操作 | 目标行为 |
| --- | --- |
| 任意设备下载新视频 | 本地立即可用，后台上传至当前选中的备份空间；不向其它提供商复制 |
| 新设备连接同一库 | 使用相同提供商及远端库定位连接，校验 `library_id` 后导入记录，不伪造本机路径 |
| 查看列表、标题、封面、已有文案 | 只获取元数据或对应小对象，不请求视频内容 |
| 播放、外部播放、明确下载 | 本地文件有效则直接使用，否则按需恢复 |
| 首次转录或重新转录 | 需要时恢复视频；计算完成后同步新文案 |
| 释放本机空间 | 仅移除本机副本，不删除远端记录或其他设备副本 |
| 从同步库删除 | 发起设备持久化意图、删除本机受管副本并发布云端墓碑；其他设备仅更新远端状态，本机已有视频继续保留 |
| 清空或移除下载历史 | 不删除本机视频、独立资产或远端内容 |
| 资源管理器移动或删除文件、磁盘离线 | 标记本机不可用，不推断为全局删除 |
| 暂停同步或离线 | 保留本机数据和待提交操作，恢复后继续协调 |
| 切换备份提供商 | 新建或连接独立备份空间；原空间的资产、凭据、版本及队列保留，旧空间作业暂停；不自动迁移旧视频 |

“从同步库删除”只在**发起设备**清理其明确选定且校验属于该资产的本机文件；其他设备不执行联动文件删除。其他设备即使离线很久，重连后也不删除已经存在的受管视频。文件被用户移动或更改、磁盘未挂载以及用户复制/导出的文件均不由同步墓碑自动清理。

释放空间不得让尚未成功备份的唯一副本丢失；存在未发布的本地内容或依赖本机文件的操作时，应等待其完成或明确阻止释放。下载完成、本机可用、云端已同步、云端逻辑删除和对象清理完成继续分别建模。

### 2.1 其他设备收到删除后的最小化规则

| 其他设备的状态 | 后台收到墓碑 | 用户实际需要读取视频时 |
| --- | --- | --- |
| 本机有效视频存在 | 在相应备份空间记为 `remote_deleted`，停止该空间此资产的自动发布、上传和远端恢复；保留文件及本地可用入口 | **直接读本机文件**，不访问远端视频，也不因墓碑删除文件 |
| 本机视频缺失，曾经由本设备成功发布该资产的视频记录 | 将远端状态记为 `remote_deleted`，从云端列表隐藏该条；不在后台清空本地记录 | 实际播放、外部播放、首次/重新转录或明确下载触发最新记录读取；确认墓碑后，清理过期的已同步投影、无效远端引用及可再生缓存，保留最小墓碑和未提交本机数据 |
| 本机视频缺失，从未成功发布该资产的视频记录（含来源未知） | 将远端状态记为 `remote_deleted`，从云端列表隐藏该条；保留本机记录和未同步数据 | 同样只在实际读取时复核最新墓碑；确认后维持隐藏及不可恢复状态，保留本机未同步内容 |
| 远端读取失败、权限不足、网络断开或对象记录 404 | 不将异常等同墓碑；保留之前可靠状态和本机数据 | 报告具体错误，不能据此执行记录清理或远端删除 |

这里的“清理”针对**过期的本机同步投影和缓存**，不是删除另一台设备的视频文件，也不是整行删除 `media_assets`。本机没有视频时，优先从云端列表隐藏失效条目；若仍有未提交标题、转录、冲突版本或其他用户数据，则必须保留并标记“本机待处理”，不可静默丢弃。

**仅有经选定提供商验证的权威墓碑（S3：同库 `records/<asset_id>.json` 中 `state=deleted`，或经同库身份及分片验证的精简删除索引；后续 Telegram：经过事件重放验证的删除事件），才能触发以上删除确认。** 单个 `GetObject/HeadObject` 的 404、媒体对象缺失、列表不完整和本机路径缺失均不构成删除证据。后台可以发现并缓存墓碑、隐藏云端行，但不执行上述按需清理；只有用户实际读取且本机视频缺失才运行按需确认。

## 3. 统一 BackupProvider 架构与独立备份空间

### 3.1 分层与复用原则

```text
React / Tauri：选择提供商、设置、列表、传输及冲突反馈
  -> SyncEngine：资产身份、变更基线、三方合并、墓碑、操作队列、按需恢复
      -> BackupProvider（业务级、提供商中立的接口）
          -> S3Provider（复用现有 ObjectStore + S3Store；R2 配置预设 / 通用 S3）
          -> TelegramProvider（预留适配入口；未来基于 MTProto/TDLib）
```

- `SyncEngine` 是应用层同步状态机：维护 `asset_id`、`operation_id`、本机待提交变更、冲突版本、删除和本机文件状态。它**不直接**使用 S3 ETag、Bucket Key、`ListObjectsV2` 或 Telegram 消息 ID 决定业务状态。
- `BackupProvider` 提供**业务语义接口**，统一返回远端库身份、可验证的变更、发布回执、带类型的媒体引用、传输进度和能力信息。允许每种实现内部保留不同的版本令牌、历史游标和续传断点。
- 保留现有 `backup/store.rs::ObjectStore` 及 `s3_client.rs::S3Store` 作为**S3 提供商内部传输接口**，其 `Condition::Match/Absent`、`Write::CompleteMultipart`、`ListParts` 等不提升为所有提供商必须模拟的公共协议。
- 首版只实例化 `S3Provider`；R2 和通用 S3 是同一个提供商实现的不同连接配置和兼容性档案，避免复制一套上传、恢复和删除引擎。
- 推荐新增 `backup/provider.rs`（公共契约与类型）及 `backup/s3_provider.rs`（包装现有 S3 对象接口）。`SyncEngine` 可复用现有 `scheduler.rs`、`reconcile.rs`、`lifecycle.rs` 的核心流程，按需抽取而非大规模重建。

### 3.2 公共语义接口

以下为 Rust 概念接口，具体签名在 P1 固定；取消信号、异步流和错误类型沿用现有工程写法，不直接把示例视为可编译代码。

| 操作 | 提供商中立的契约 | 关键返回/错误 |
| --- | --- | --- |
| `capabilities()` | 查询已验证的多设备写入、变更发现、媒体限制和续传能力 | `ProviderCapabilities`，不允许乐观默认开启 |
| `open_library(create_or_connect)` | 新建或连接指定备份空间，并校验库身份与协议版本 | `LibraryDescriptor`，区分库不存在、权限失败、协议不兼容 |
| `pull_changes(checkpoint)` | 拉取可验证的资产变化/墓碑，返回新的**提供商不透明检查点** | `ChangeBatch`；分页失败不当作完整空库 |
| `publish_change(change, base_token, operation_id)` | 按提供商真实提交语义发布资产变更或删除事件 | `PublishReceipt`，区分“传输已接受”“已确认收敛”“冲突/待重试” |
| `upload_media(asset, source, resume_state)` | 上传视频/封面/文案的不可变内容并返回可持久化引用 | `MediaRef`、大小、SHA-256、提供商私有续传断点 |
| `download_media(media_ref, offset)` | 按引用与偏移流式恢复，实际支持由能力信息判定 | 流、长度/版本/校验信息、明确不可恢复错误 |
| `delete_media(media_ref, operation_id)` | 删除已确认属于当前库资产的媒体引用 | 幂等清理回执；不触及其他空间 |
| `reconcile_deleted_asset(asset_id, operation_id)` | 发现、核验并回收该库墓碑资产的旧版本/晚到媒体，保存清理断点 | 可恢复清理进度；由提供商内部执行范围约束 |

公共 `AssetChange` 定义新增、字段补丁、文案引用更新和墓碑删除；**字段未修改**与**明确设置为 null**必须区分。公共 `VersionToken`、`Checkpoint`、`ResumeState` 为不透明且带 `space_id + provider_type` 的封装，跨提供商、跨空间及协议版本不能互用。

**成功语义不能混同**：S3 条件写成功可确认对应远端记录已提交；未来 Telegram 的消息发送成功只代表事件被接受，仍需同步日志重放后确认当前资产投影已收敛。统一 UI 的“已同步”以该资产提交变更被提供商确认并能由同步引擎重建为预期状态为准，不能把单纯“媒体上传完成”或“消息已发送”直接显示为最终同步成功。删除墓碑的权威性也由提供商具体实现验证，不能仅依赖媒体不存在。

### 3.3 提供商能力与功能门禁

| 能力 | Cloudflare R2 | 通用 S3 | Telegram（未来） |
| --- | --- | --- | --- |
| 资产变更协调 | `PutObject` 原子条件写 | 必须验证 `If-Match/If-None-Match` 的真实并发行为 | 私有索引频道追加事件、顺序重放与确定性冲突合并 |
| 变更发现 | `ListObjectsV2`、ETag 缓存 | 分页列表与版本令牌经验证后使用 | 消息历史/更新游标，须验证缺页及重放 |
| 视频上传/恢复 | 单次或多分片上传，Range | 依据服务具体分片/Range 行为 | MTProto 分块传输，受账号与单文件限制 |
| 媒体位置 | `S3ObjectRef`（Bucket/Key/摘要） | `S3ObjectRef` | `TelegramMessageRef`（账号/频道/消息身份及摘要） |
| 删除证据 | 已验证同库的 record 墓碑 | 同左，须通过能力门禁 | 经过重放验证的 `AssetDeleted` 事件 |
| 首版实现状态 | 复用已实现的 S3 客户端，改造多设备协调 | 同一 S3Provider，测试兼容性后启用 | 仅预留契约，保持不可选 |

`ProviderCapabilities` 至少覆盖 `change_coordination`（条件写/事件重放）、`incremental_discovery`、`range_read`、`resumable_upload`、`max_single_media_bytes`、`can_delete_owned_media`。**不是为所有提供商强行寻找一个最小公共 S3 API**。某服务若无法验证原子条件写或等价的变更协调，拒绝启用多设备写入，提供具体不支持原因；不能默默退化为“最后一次覆盖获胜”。

Cloudflare R2 已公开支持 `PutObject` 的原子条件头；AWS S3 也有条件写入契约，个别兼容服务可能实现不完整。自定义 S3 Endpoint 首版要求 HTTPS、禁止在 URL 中携带账号口令并限制跨域重定向；系统凭据按空间隔离，不向未经验证的其它目标发送认证信息。通用 S3 的测试连接须在**明确授权的隔离探针键**验证读、列表、条件创建、版本匹配/拒绝、删除、按需 Range 和分片（仅在对应功能启用前）；不能把仅成功列举 Bucket 视为同步兼容。参考 [R2 API 兼容性](https://developers.cloudflare.com/r2/api/s3/api/) 与 [AWS S3 条件写入](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)。

### 3.4 独立空间、选择与切换

- 本地保留既有 `backup_spaces.space_id` 作为**设备本机的空间配置 ID**；增加 `provider_type`（`s3` / `telegram`）、`provider_config_json`（S3：`endpoint/region/bucket/prefix` 加 `r2/generic` 预设；Telegram：未来账号与私有频道定位）、`credential_ref` 以及状态。现有 R2 配置通过数据库迁移映射为 `provider_type=s3, profile=r2`，保留原 `space_id`、凭据引用和待完成任务。
- 远端 `library_id` 是设备间识别同一逻辑库的依据；同一库必须使用**相同提供商与远端定位**。跨设备 `space_id` 可以不同，不能当作远端身份。远端库描述必须校验提供商、协议及 `library_id`。
- 首版**同一时刻仅有一个当前自动同步空间**。用户可保存多个独立空间配置；设置顶部 Tab 用于查看和编辑，新配置保存后增加 Tab，查看和保存非当前空间不切换默认渠道。只有底部“切换空间”才实际选择另一空间，将旧空间的写入/恢复队列安全暂停并持久保留，旧空间的资产映射、墓碑、冲突、上传来源证明及历史凭据继续归属旧空间。切回旧空间后核验库身份，再恢复其待处理操作。
- 新空间是独立的备份库：不会因为本机曾在 R2 备份过一条视频，就在连接 Telegram 或另一 S3 Bucket 后把该视频自动重传过去。切换后**新产生的受管完成视频**归属新空间；旧资产只有在以后通过用户明确选择的迁移/手动备份操作才进入新空间。本轮不实现跨提供商搬运、同步镜像或自动合库。
- 远端资产状态、`asset_id` 关联、`ever_uploaded_by_this_device`、本机同步基线、墓碑与操作日志至少按 `space_id + asset_id` 隔离。**远端资产的完整身份是 `(library_id, asset_id)`，本机通过 `(space_id, remote_asset_id) -> local_asset_id` 的关联表或等价键映射到已有 `media_assets`；不能直接假定不同库的远端 UUID 全局唯一。**已有全局 `media_assets.asset_state` 不能因一个**非当前**空间的墓碑而改变另一空间的资产可用性。迁移必须防止跨库同名 `asset_id` 复用同一业务记录及其文案。
- `backup_operations` 含 `space_id`、`provider_type` 快照和后端目标指纹；执行、取消、续传与重试前必须核验三者一致。绝不把旧 R2 的 ETag、对象键、`upload_id` 或删除待办送到 Telegram / 另一 Bucket。切换时不得顺手清理旧 Bucket，撤销凭据之前必须处理可恢复的旧空间操作。
- 仍保留现有“本地文件存在直接使用、缺失且实际读取才访问远端”的懒加载与按需墓碑确认。云端列表、冲突状态、删除后的隐藏规则全部以**当前选定空间**呈现。退出/切页不会改变空间归属。

### 3.5 Telegram 后续适配的最小边界

TelegramProvider 将视频、封面、转录和索引事件**全部放在用户选定的 Telegram 私有空间**，不借助 R2 保存元数据。未来需要专用索引消息序列（`LibraryCreated`、`AssetChanged`、`AssetDeleted` 等）、`operation_id` 幂等、消息顺序重放、可恢复检查点、确定性合并与墓碑验证；媒体引用绑定账号/频道/消息身份，并通过原消息刷新可能过期的 `file_reference`。

Telegram 消息追加没有 S3 的 `If-Match` 语义，不能把消息 ID 伪装成 ETag，也不能把消息不存在当作明确删除。跨设备最终收敛、重复事件与未知发送结果，均需要 Telegram 专项测试后才允许启用。现有 `tdl_bridge.rs` 是**平台视频解析和下载通道**，不是可直接用作备份同步的 TelegramProvider；未来应另行评估 MTProto/TDLib 的独立会话、上传权限、文件大小、限流、索引消息可见性与恢复稳定性。

参考 [Telegram 消息历史](https://core.telegram.org/method/messages.getHistory)、[Telegram 文件传输](https://core.telegram.org/api/files)、[Telegram 文件引用](https://core.telegram.org/api/file-references)。本轮**只定义契约、配置结构和禁用门禁**，不新增 Telegram 登录、频道创建、媒体上传或在线测试。

三个必须修正的具体问题：

1. 上传前读取最新 ETag 后仍以本机整条快照覆盖，虽然满足条件写，却可能丢失另一设备已经提交的字段。必须保存修改基线并合并实际变化。
2. 现有 `published_signature` 不能区分远端导入、本机恢复和真实本地修改。直接开放上传会产生反复发布或旧文案回写。
3. `cleanup_canceled` 当前枚举同一对象键的全部分片会话。普通取消必须只中止自身持久化的 `upload_id`；发起删除的设备在确认墓碑后，才可按精确资产前缀清理远端对象和会话。其他设备发现墓碑后仅终止**自己拥有**的在途上传。
4. 同步删除必须区分云端墓碑、本机文件可用性、上传来源以及“已提交/未提交”的本机数据；后台墓碑导入绝不能直接执行其它设备的文件删除或清空资产记录。

## 5. 同步协议与 S3 条件发布

**以下对象布局和 CAS（比较并交换）规则只适用于 S3Provider。** S3 继续使用固定 `library.json`、按资产独立的 `records/<asset_id>.json` 及现有不可变媒体/文案对象；远端库和资产记录统一使用当前唯一存储格式，模式为 `multi_writer`。公共的资产变更、删除和冲突语义由 SyncEngine 定义，Telegram 未来使用独立的日志定位与重放实现。具体序列化字段、提供商身份与迁移映射在 P1 固定。

记录至少保留库 ID、资产 ID、状态、修订号、媒体引用、封面引用和文案引用；新增修改设备和幂等操作标识。冲突版本须通过资产记录中的引用发现，不能只留在某台设备数据库或成为不可发现的孤立对象。

发布顺序：

1. 在本地事务中登记操作 ID、基线记录及 ETag、本地实际变化；网络操作前持久化必要断点。
2. 上传所需的不可变内容对象；仅更新元数据时，不要求本机存在视频，不重传视频。
3. 读取最新记录，与基线、本地变化进行三方比较。
4. **S3Provider 内部**：创建使用 `If-None-Match: *`，更新使用当前 ETag 的 `If-Match`；公共协调层仅持有不透明 `VersionToken`。
5. **S3Provider 内部**：`412` 触发重新读取和合并，有限重试后保留待处理状态；不能把旧快照换个 ETag 后直接覆盖。通用 S3 另处理其实际返回的条件冲突码；未来 Telegram 则从事件日志重放并确定性合并。
6. 成功后事务更新同步基线，只确认本次提交包含的本地变化；提交期间新增的变化仍待同步。
7. 响应丢失时回读并核验幂等标识和内容，不能仅凭一次 404 宣告写入失败。

单资产记录是逻辑可见性的入口。不同资产独立发布，不用设备时钟决定版本先后。同一资产的视频内容在登记后保持不可变；新内容或另一清晰度应形成新资产，不在这轮引入原地视频编辑同步。

R2 的 `PutObject` 条件检查与写入提交是原子的，支持该协调方式；它不提供媒体对象和记录之间的跨对象事务。公开依据：[一致性与条件写入](https://developers.cloudflare.com/r2/reference/consistency/)、[S3 扩展](https://developers.cloudflare.com/r2/api/s3/extensions/)。这些依据不替代 P6 的实际并发测试。

## 6. 本地模型与冲突策略

在现有模型上增加以下逻辑数据，优先复用表和操作日志，不另建第二套队列：

| 数据 | 用途 |
| --- | --- |
| 已同步基线记录与 ETag | 确定本机修改依据，与远端新版本比较 |
| 本地待提交变化及本地修订 | 区分本地修改与远端导入，避免发布确认吞掉新修改 |
| 操作 ID 与对象、分片会话归属 | 幂等提交、续传和取消隔离 |
| 冲突版本及云端引用 | 保存不同文案或字段结果，在其他设备也可查看 |
| 同步拉取进度与删除操作 | 故障恢复、分页刷新、发起设备远端对象回收及按需记录收敛 |

所有同步状态按库/空间和资产绑定。配置切换不能把旧队列、基线或清理请求发送到新目标。**本机当前自动同步空间决定新增视频归属；旧空间历史资产继续隶属其原空间。** 本机绝对路径、下载任务 ID、播放位置及临时缓存不作为跨设备资产修改上传。

**上传来源只在本机记录**：对每个 `space_id + asset_id + device_id` 持久化 `ever_uploaded_by_this_device`（或等价的成功发布证明/操作 ID）。仅当**本设备视频内容已成功上传且活动资产记录成功发布**，或提交响应丢失后通过云端记录与原操作标识复核成功，才可写为真；下载、仅恢复视频、读取元数据、从远端导入、重新转录和仅更新元数据均不能写为真。该证明不随云端列表隐藏或下载历史清理丢失。历史迁移没有可靠成功证据时记为 `unknown`，按“未上传过”保守处理，不能依据本机有文件或 `published_signature` 单独猜测。

同时分离 `remote_deleted`（远端墓碑已确认）、`local_present`（本机仍有有效文件）、`cloud_list_visible`（云端列表是否可见）及 `has_pending_local_changes`（未提交的本机数据）。远端导入、封面缓存与视频恢复均不得触发上传来源记录，也不得将未提交变更覆盖为远端快照。

远端导入、封面缓存和视频恢复只更新缓存/本地可用性，不登记本地待提交变化。自动入队从“扫描所有本机文件”改为消费实际本地变更；必要补扫必须遵守同一规则。

| 并发情况 | 合并规则 |
| --- | --- |
| 不同资产更新 | 各自提交 |
| 同一资产不同字段变更 | 基于共同基线合并 |
| 同一字段变成相同内容 | 视为同一结果，不产生重复冲突 |
| 同一字段产生不同内容 | 保留已提交的当前值，将另一结果保存为可同步的冲突版本 |
| 两台设备重新转录得到不同结果 | 当前文案与冲突文案均可发现、读取；不静默丢弃任一结果 |
| 一方删除、另一方修改 | 墓碑阻止原资产再次发布；另一设备未提交的改动保留在本机待处理记录中，不因远端删除而丢失 |

没有共同基线时，不假定本机快照可以覆盖现有云端值。先建立基线；可证明等同则确认同步，确有差异则保留冲突，不凭本机时间裁决。选择采用某个冲突版本也是新的条件提交。无冲突的正常更新仍按既有语义发布，不扩展完整历史版本管理。

## 7. 云端删除、其他设备按需收敛与远端清理

### 7.1 发起设备的删除

任意设备可以显式执行“从同步库删除”：先持久化删除意图、停止该设备同资产的上传/恢复，再对**该设备明确选定的受管理本机文件**执行现有安全删除，条件写入云端墓碑，并启动持久化远端对象清理。其他设备不因此收到任何“删除本机文件”命令。删除发起者离线时只允许显示“云端待删除”，不能宣称其他设备同步完成。删除操作重试幂等，`412` 回读合并，删除优先；未启用自动清理时墓碑长期保留，启用后按空间保留天数合并至精简删除索引。

墓碑是单资产逻辑删除的权威证据；单资产当前记录中的 `state=deleted` 阻止所有设备基于旧快照重新提交 `active`。其他设备发现墓碑时，停止同一 `asset_id` 的待上传/远端恢复与文案发布，保留本机已存在的有效视频文件。**若本机存在未提交的标题、转录或冲突版本，先原样持久化为本机待处理内容；不经用户显式决定，不重新关联旧 `asset_id` 上传。** 用户点击“重新上传”时，使用新操作发布较新的活动修订并保留本机修改，不将索引作为永久禁传名单。

### 7.2 其他设备的按需读取与记录清理

```text
B 设备需要实际读取视频（播放 / 外部播放 / 开始转录 / 明确下载）
  ├─ 本机文件存在且验证有效 → 直接返回本机路径；保留副本
  └─ 本机文件缺失
       ├─ 最新云端记录 active → 原有 Range 恢复与完整性校验
       ├─ 最新云端记录 deleted 且已校验 library_id / asset_id
       │    ├─ 本机曾成功上传 → 清理已同步投影及可再生缓存；保留最小墓碑与未提交数据
       │    └─ 本机从未成功上传或来源未知 → 云端列表隐藏；保留本机数据
       └─ 读取失败、无记录或证据不完整 → 不清理记录，返回具体错误
```

后台同步继续允许读取元数据和墓碑；对**本机缺失且云端已删除**的资产，云端列表应立即隐藏（不必等用户点击），但后台不触发按需记录清理、文件 I/O 或新的对象删除。若本机视频有效，云端状态同样记为已删除，但本机文件可在现有本地入口继续访问。必须保存最小墓碑/同步阻断状态，防止隐藏云端列表后旧任务再次自动上传。

在确认墓碑后：
- **曾上传**：仅删除可由远端重新计算的缓存、过期云端引用、已同步的投影数据；保留最小墓碑、上传来源证明、尚未提交的任何本机修改、转录及其它不可再生内容。不得直接级联删除 `media_assets` 或本机下载历史，除非明确证明不存在用户数据并符合既有业务契约。
- **未上传或来源未知**：不运行投影删除，仅标记云端已删除并从云端列表隐藏；已保存的本机文案、标题、待提交操作和冲突版本保持可查询。
- **本机仍存在文件**：无论上传来源，均不清理其本机副本，不因墓碑而强制恢复或进行视频网络请求。

同一墓碑重复刷新、重复实际读取和应用重启均幂等。磁盘未挂载、本机文件被用户移动或本机路径缺失，只影响可用性，不等于远端已删除。若另一设备曾持有的文件在确认墓碑前恰好恢复成功，不能在后续后台刷新中将其自动删除。

### 7.3 远端物理对象回收

云端删除记录与对象清理仍是两个阶段。**发起删除的设备**通过当前提供商的删除/清理接口处理**同一个 `space_id` 内**的已确认媒体引用。S3Provider 复用持久 `delete` 操作按该库精确 `asset_id` 前缀清理当前及旧视频、封面、转录、冲突版本和已确认属于该资产的分片；不能只依赖本机 `backup_owned_objects` 清单。未来 Telegram 只清理该频道、账号已核验属于此资产的媒体消息，墓碑事件须保留。删除期间其它设备可能仍有在途上传，所有客户端发现墓碑后应停止**自身**同资产上传并中止自己的 `upload_id`，不能为了“同步删除”取消别人的会话。

发起设备以持久化状态继续执行有限次数的延后对账，后续启动也能重试晚到对象；一次扫描为空不能证明所有在途写入永久结束。**首版不要求任意另一台设备自动接管发起者的远端物理回收**，也不为按需读取额外发送远端 `DeleteObject`。若发起设备长时间离线，可能暂时遗留不可见的孤儿对象并继续占用 R2 空间，直到其恢复清理或用户显式执行维护。界面区分“云端已逻辑删除”与“远端清理完成”，不承诺跨设备即时物理清理。

### 7.4 删除记录保留与压缩

每个本机空间配置增加默认关闭的自动清理及1～3650天保留时间（默认30天），存入幂等补建的`backup_record_retention`表，不改变现有SQLite版本和资产/操作身份。新墓碑记录删除时间，历史无时间墓碑从首次检查开始计时。现有Rust维护循环仅处理当前启用空间的已确认删除记录，正常每小时、失败5分钟后重试，切换/停用取消当前清理，回切继续；不依赖任务页面，不增加服务端或第二套队列。

S3Provider先CAS合并到`deletions/<UUID前两位>.json`，保留资产ID、修订号、删除时间和操作/设备ID；确认后用`DeleteObject If-Match`移除原独立JSON，仅清理已删除记录，活动记录不按天数删除。`library.json`的可选索引存在标记避免默认空间增加空目录扫描；已存在索引分页并按ETag跳过未变化分片。记录缺失时读取索引确认删除，任何普通404仍不能单独认定用户删除。删除索引持久保留，不强制引入设备离线期限或额外防重复上传协议。

重新上传使用较新的活动修订，活动JSON优先于历史索引，后续重复删除可再次合并新的墓碑。旧删除任务在后续复查发现活动记录时结束，不重新发布墓碑。 重新上传文件使用被替换删除修订号下的独立不可变路径`media/<asset>/<kind>-r<删除修订>-<SHA256>.<ext>`；旧清理只处理更早修订的文件和会话，不触碰当前重新上传。已经发布墓碑的复查阶段不再重复发布删除；显式新删除重置复查次数。发布前若删除修订已经改变，则保留本机数据并要求重新上传，不发布指向过期清理范围的文件。所有规则只复用单资产现有修订，不引入设备期限、上传次数限制或全局锁。

重新上传将未解决的本机冲突继续发布并保留导出入口；引用的旧冲突文件即使已经清理，也保留完整引用，详情明确不可采用并可导出，不静默删除冲突记录。用户尚未同步的标题、转录和冲突仍按本机待处理契约保留。

## 8. 后台同步与懒加载

Rust 后台服务负责**当前选定空间**的拉取和提交，React 不承担同步正确性。启用及启动后异步刷新，前台活跃建议约 30 秒轮询，隐藏/空闲时约 2–5 分钟轮询，失败退避；支持手动刷新、本地改动即时唤醒。远端枚举通过 `BackupProvider.pull_changes`，S3Provider 内部使用分页对象列表和 ETag，未来 Telegram 使用其专有历史游标。周期由代码内部管理，不新增用户必须理解的调度设置。网络调用不持有 SQLite/Core 互斥锁。

复用分页列举与 ETag 比较，只读取变化记录。分页中断后可重试并幂等导入，列表暂时缺失不推断为删除；多页列举也不视为全库事务快照。先采用完整分页扫描，不新增全局变更日志，承认资产数量增长会增加列举成本。

下载或转录完成、用户删除等本地动作及时唤醒提交队列。大视频传输不能长期阻塞元数据拉取和墓碑接收；复用既有服务生命周期和取消机制，不为每个页面另起同步循环。隐藏窗口或切换页面不影响同步，退出必须结束实际操作并保存断点。

视频恢复沿用本地优先、Range、目标卷暂存、媒体头/大小/SHA-256 校验及不覆盖提交。目录浏览和常规同步不得请求视频内容；已有文案读取无需恢复视频。**本机文件有效时，播放只读本机文件；本机缺失才对最新远端记录进行按需判定。**恢复提交前检查最新墓碑，已确认删除则不提交远端恢复结果；若先恢复成功、后收到墓碑，保留现有本机副本并只更新远端状态。后台墓碑刷新只更新同步状态和列表可见性，不自动删除物理文件、资产数据或未提交本机变更。

## 9. 设置与交互

- 删除主设备/恢复设备选择及所有角色控制的按钮分支。增加“备份提供商”选项：Cloudflare R2（S3 预设）、通用 S3（通过能力探测后启用），以及明确标注“规划中”的 Telegram（当前不可连接、上传或执行测试）。每次只激活一个自动同步空间；已保存的其他空间可重新选择。
- 每台设备为**当前空间**使用相应凭据，沿用系统凭据库：R2/S3 使用对象存储访问密钥，Telegram 未来使用独立账户会话；权限不足明确提示。设置返回和事件不得暴露任一提供商的 Secret/会话信息。
- 保留输入后直接测试、密钥掩码与眼睛、按钮忙碌反馈及 Toast。若测试宣称可双向同步，须由所选提供商探测必要读、条件提交/事件提交及删除能力；S3 探针仅使用已授权的隔离随机键并清理，不创建真实资产或改写库元数据。
- 保留标题前的小图标、上传圆环、恢复进度、原地悬停反馈、Tooltip 及右键传输操作，不新增独立云端页面。
- “释放本机空间”与“从当前同步库删除”明确区分：后者只影响**当前空间**的云端资产与操作发起设备的受管文件；其它空间的资产状态及其它设备已保存的本机副本继续存在。切换提供商时说明旧库仍保留、旧队列暂停、媒体不自动迁移；沿用项目已有必要确认交互。
- 冲突不自动弹强制选择框，任务状态可见并提供“查看冲突版本”入口。云端已删除的缺失文件从云端列表隐藏；若有本机未提交修改，保留可见的本机待处理入口。Toast 用于操作通知，不能代替持久失败/冲突状态。
- P5 同步更新 `DESIGN.md`，不提前把当前实现文档写成已完成。

## 10. 单一协议与连接初始化

R2/S3 尚未发布，只提供当前的多设备同步协议，不提供格式版本选择、升级页面、凭据替换确认或客户端迁移流程。协议的内部序列化校验值不作为产品版本展示。

保存配置、启用当前空间或设为默认时，复用已保存的系统凭据，校验目标能力及库身份，并通过条件写初始化当前格式。开发期间已产生的本机配置和对象元数据由同一连接流程整理，保持 `space_id`、`library_id`、远端资产 ID、对象键、媒体内容和未提交文案不变；不复制或重新上传视频。中断时使用对象内的持久操作标记继续，不创建第二套队列或运行期全局锁。

普通连接测试只执行隔离能力探针，不改写库元数据；启动本机 SQLite 结构初始化也不操作远端。已按当前格式工作的库继续沿用 CAS 与作用域验证。未确认的上传结果保留待复核状态，不重放未知会话，不从 404 推断删除；已有基线、冲突、墓碑及当前格式的队列断点不被初始化覆盖。

## 11. 验证与交付边界

按 P1–P6 顺序推进，每阶段实现、必要测试和验收完成后进入下一阶段。最少使用两个独立数据库、不同 device_id、不同本机文件目录和同一个可控对象存储验证多设备行为；单数据库两个请求不能替代多设备测试。

重点覆盖并发条件写、离线重连、导入不回写、提交中发生新修改、冲突跨设备可见、取消隔离、删除与上传/恢复交错、崩溃续跑和旧库迁移。**必须增加同一设备两个不同空间的切换验收：旧空间任务冻结、连接回切恢复、仅新视频进入新空间、旧墓碑和旧本机上传证明不污染新库、不同 Bucket/Prefix 对象操作隔离。****删除验收必须分别覆盖：B 本机文件有效、缺失且曾上传、缺失但从未上传或来源未知、后台先见墓碑后实际读取、网络异常 404、未同步文案保留。**断言后台刷新不会执行另一设备本机文件删除或按需投影清理，也不会出现删除后的自动上传回声。故障按可控请求交错注入，不用不稳定的 sleep 竞速作为主要断言。

真实 R2 测试只使用已授权 `s3-r2-test.local.json` 指定的测试 Bucket 和前缀；若需验证通用 S3，使用另行授权的隔离测试空间。每次在目标内部建立独立 run 子前缀，清理只针对本次所属对象与会话。不更改 Bucket 全局策略，不读取用户视频，不输出密钥。离线、真实 R2、浏览器、原生 Tauri、安装包及各操作系统结果分别记录，未运行标记 `NOT_RUN` 或 `UNAVAILABLE`。

本文件只记录拟实施方案；首版交付按 S3Provider 的功能与兼容性探测验收，TelegramProvider 仅保留设计契约与未来接入门槛。底层对象存储测试不能计为多设备同步、跨提供商隔离或 Telegram 同步已通过。
