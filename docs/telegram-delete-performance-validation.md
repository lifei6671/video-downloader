## 本轮验收

### 从用户操作到界面移除

1. 用户在下载任务页的资产操作菜单点“从当前同步库删除”。React 调用 `api.deleteAsset`，Tauri 的 `delete_asset_and_backup` 返回 SQLite 操作 ID。这个回执表示请求已受理。
2. `sync_delete::intent` 在事务内保存删除任务、当前空间和远端资产身份，标记同资产上传与本地显示状态。提交后 `delete_queue_wake.notify_one()` 唤醒队列，取消仅涉及同资产的恢复和转写。重复点击同一进行中的 Telegram 删除沿用其操作 ID 和退避期限。
3. `sync_engine::queue_loop` 在当前空间优先选到期的前台删除，有删除时跳过普通上传发现。最终选取与领取持同一数据库锁。已有上传继续执行，`archive_ready` 后继仍优先，失败任务自行退避。队列处理一次失败后立即查看其他到期项。
4. `sync_delete::execute_inner` 获取备份写锁，发布可重放的墓碑归档，重新读取当前映射、核对删除代次、活跃引用、频道与消息归属。若有已确认的相邻删除，按原协议交接归档。旧索引与原消息成功确认消失、复查远端状态后，才进入 `finish_local`。
5. `Core::finish_asset_deletion` 在同一事务提交隐藏记录、本地任务移除和 `local_cleanup_done`。提交后向 WebView 发送 `backup_asset_deleted`。React 重新读取当前空间，用现有退出动画移除行。漏事件时原有轮询仍工作。后续 30/120 秒的 `cleanup_verify` 由后台执行。

操作 ID 贯穿原生日志、SQLite 和 WebView 事件。首次真实队列领取使用 `first_claimed_ms`，每次领取记 `queue_claim`。事务提交返回记 `intent_committed`。各阶段的 `ended_ms`、成功阶段的会话等待结束点和本地提交标记使用同机 UTC 毫秒。耗时细分由 Rust `Instant` 测量。浏览器端从可信点击到 DOM 移除使用同一 WebView 的 `performance.now()`，另记下一渲染帧。按操作 ID 对应前后阶段，不能跨进程相减两个单调时钟。墙钟只用于同机对齐，父阶段包含子阶段，批处理的网络工作只计算一次。

### 锁、归档与队列改动

### 双设备与富消息的真实回归

### 剩余瓶颈与证据位置

正常热删除的 9 s 目标仍差 0.684 s。新归档至少有一次远端发布和一次验证正文回读，二者均直接关系到能否从远端重放原始事件。密集点击的主要等待来自同空间前序归档，20 条中第 10、11 条的慢正文回读放大了后续等待。进一步优化应先用同一归档规模、相同点击间隔比较基线，再评估让多条墓碑一次发布的收益与恢复代价；需要保留每条操作的原始事件、独立代次和部分失败重试。

当前机器的忽略目录 `.local/telegram-delete-e2e-1102/` 保留了脱敏证据。严格桌面组的逐次点击、阶段与首领时间在 `desktop-strict-20.redacted.json`、`desktop-strict-phases.redacted.json`，带首条间隔的首轮在 `desktop-interrupted-20.redacted.json`。原生分组的逐样本阶段和前后请求计数在 `native-delete-samples.redacted.json`、`native-rpc-steps.redacted.json`，同资产下载和三个无关传输组分别在 `concurrent10.redacted.json`、`unrelated-transfers.redacted.json`。公开报告不包含账号、频道、消息 ID 或私有配置。
